1判断フロー ── 定量ゲートつきv2

タスク受領
 ├ 段階0：決定論（regex / SQL / ルール / ETL）で足りる？  → YES: LLMを使わない   ★v2追加
 ├ 段階1：単一LLM呼び出し（+tools / examples）で足りる？ → YES: それで終わり（最頻）
 ├ 段階2：知識参照が要る？                              → RAG-first（§Security&RAG）
 ├ 段階3：固定的な多段か？                              → workflow（chaining / routing / parallel）
 ├ 段階4：制御は固定だが一部に判断が要る？             → hybrid（一部ノードだけagentic）★実務の主役
 ├ 段階5：ステップが動的・全面分岐？                    → 単一 agent（ReAct）
 └ 段階6：multi-agent ROIゲートを全て満たす？           → multi-agent（orchestrator-workers）

multi-agent移行ゲート（全て満たすとき限定）：情報量が1コンテキスト超 ／ 独立サブタスク概ね3以上 ／ 失敗コストが高い高価値 ／ 単一agent evalが閾値未達 ／ ROIが正（次節）。
※workflowとagentは直線的発展段階ではない。制御はworkflow・判断だけagent のハイブリッドを中心に（5.5 Pro指摘）。

分解の粒度 & sub-agent契約

粒度：単純事実探索＝1agent/3-10呼出 ｜ 比較＝2-4 sub/各10-15 ｜ 複雑＝10+ sub。

sub-agentに必須① 目的② 出力形式③ ツール/情報源④ タスクの境界＋ schema強制I/O＋ context isolation

3パターンカタログ（Anthropicの5型）

Prompt chaining

逐次分解、各段の間にgate（検証）。固定段に分解でき各段の精度を上げたい。

Routing

分類して専用処理へ。入力が明確なカテゴリに分かれる。

Parallelization

並列分割（sectioning）or 多数決（voting）。高速化／信頼性。

Orchestrator-workers

動的分解→委譲→統合。サブタスク数が事前に読めない。

Evaluator-optimizer

生成→評価→改善ループ。明確な評価規準があり反復で質が上がる。

Augmented LLM（基礎）

LLM＋retrieval＋tools＋memory。すべての出発点。

LangGraph docs も同型のworkflow/agentパターンを提示（「5パターンを名前付き公式実装」とは言い切らない＝5.5 Pro指摘）。「gather→action→verify」はAnthropic後の framing。

4信頼性・制御・人間の監督

  • ハイブリッド制御：決定的（分岐/ループ/fan-out）＋モデル適応（判断所のみLLM）
  • retry + checkpoint + resume・冪等性 ／ 多層guardrails（relevance/safety/PII/moderation/blocklist/出力検証）
  • HITL承認ゲート（不可逆・高影響の前） ／ stopping conditions（最大反復・予算上限・K回連続で新発見ゼロ）
  • 自己レビュー≠独立検証 → 敵対的検証を別エージェントで ／ ポカヨケ（schema強制・型・列挙）

★Security & RAGv2新設

RAG文書は「信頼できる知識」ではなく、プロンプトインジェクションを含み得る外部入力。検索結果をそのままagentの指示として扱う設計は危険（5.5 Pro：S優先・別章必須）。

Security

tool権限階層・read/write分離・sandbox・allowlist・data exfiltration防止・human approval。RAG文書を不信入力として扱う。toolを持つagentは攻撃面が広い。

RAG統合

hybrid search・reranking・citation extraction・source quality scoring・staleness / cache invalidation・connector権限。multi-agent探索とstatic RAGの組合せが設計の分岐点。

  • step-wise ＋ end-to-end の両建て。eval自動化：golden tasks・regression・capability eval・trace replay・pass@k/pass^k・LLM-judge calibration・production monitoring

6コスト・モデル選択・コンテキスト

prompt caching（出典分離）

「90%コスト減・85%レイテンシ減・11.5s→2.4s」＝news/prompt-caching 記事。read 0.1×/write 1.25×(5分)・2×(1時間)＝Claude docs 料金/TTL（5.5 Pro指摘）。

model tiering

Haiku/Sonnet/Opus。安いsub-agent＋Opus orchestrator。まず高能力でベースライン→落とせる所を小モデルへ。

context engineering

compaction・note-taking・sub-agentのクリーン文脈・memory tool。context rot を防ぐ。

フレームワーク：graph(LangGraph) / conversation(CrewAI,AutoGen) / code(OpenAI Agents SDK・Claude Agent SDK※具体記述はdocs時点依存) / optimization(DSPy) / durable(Temporal)。まずLLM API直叩き、合うときだけframework。

7アンチパターンと「使うべきでない」場面

設計レベル

決定論で足りる所をagent化／不要な増殖・過剰分解／フレームワーク過剰抽象／"Bag of Agents"。

実行時の崩壊

context bloat/rot／silent truncation／"Token Spiral"（$2,847/4時間）／cascading hallucination（17.2×／中央集権で約4.4×）／検証なしfan-out。

使うべきでない：低価値・高頻度、密結合で逐次依存、決定論で書ける手続き、レイテンシ厳守。

★一次経験：失敗の教訓（5.5 Proが最高評価）v2一般化修正

「AIワークフローの作り方」をワークフローで調べさせたら3本とも StructuredOutput で落ち、最も価値ある一次教訓を生んだ。研究は完遂・検証段は捏造を実際に検出。これは複合障害である：
観察された失敗より一般的な原因
socket connection closedtransport / infrastructure failure
malformed tag（<corrected_findings">反復）serialization / schema contract failure
final synthesis failhigh-entropy aggregation failure
研究結果は残っていたraw artifact preservation が機能
transcriptから回収できたrecovery-oriented design が有効

一般化（v1「主ループで統合」を修正）：本質は「sub-agentが弱い」でなく最大コンテキスト・最大出力・最大スキーマ制約を最後の一発に集中させたこと。∴ 最終統合は「最も信頼できる制御プレーン」に置く（人間／決定論coordinator／chunked synthesis）。巨大な最終JSONを作らない ── 各subは「短いmanifest＋raw＋source map」、coordinatorはmanifestだけ集約、最終はJSONL/小schema分割。

①schemaフラット②段階統合（巨大JSON回避）③回収前提④裸agentはthrow→null化/try-catch⑤研究深度cap＋リトライ⑥敵対的検証

8Source hygiene ＆ 検証の再帰

各数値claimに source・version/date・scope・generalizability を付す（5.5 Pro最優先改訂3）。理由＝MASTはv1/v2で数値が変わり、Anthropicの+90.2%等は内部評価・read-heavy限定、prompt cachingはnews/docsで出典が分かれる。
