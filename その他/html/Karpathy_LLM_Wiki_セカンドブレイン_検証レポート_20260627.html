要旨（ABSTRACT）

Andrej Karpathy が公開した LLM Wiki / Personal Knowledge Base Pattern は、従来のRAG（毎回ベクトル検索して一時回答を生成）とは発想を異にし、AIエージェントが 永続するMarkdown Wikiを生資料とユーザーの間に増分的に構築・保守する アーキテクチャである。三層（raw sources／wiki／schema）と三操作（Ingest／Query／Lint）から成り、Vannevar Bush の Memex（1945）の「参照保守の手間」をLLMで解決した点に新規性がある1。本稿は本パターンを批判的に検証し、(1)「15分でセカンドブレイン完成・コーディング不要」は接続までの話で、研究運用には誇張であること、(2) RAGの代替ではなく RAGの上に置く知識編集レイヤーであること、(3) 法学博士論文用途では 原資料・脚注・典拠のimmutable化が品質の分岐点であること、を示す。あわせて、利用者が既に保有する OCC_Vault（84ノート・10桁分類）と ChromaDB RAG・判例DBへの層分け実装設計と、実機検証で判明した実装手順の誤り（gitルートの所在）を補正した「今夜の最小手順」を提示する。

I結論 ― 使えるが、宣伝は誇張

本パターンの核は地味だが正しい。Claudeエージェントをディレクトリ上で起動し、Markdown群を grep（全文走査）で読ませ、作法を CLAUDE.md に書く、というだけのものである。これは利用者がCFC博士論文の執筆で日々行っている運用と実質的に同一であり、その意味で「使えるか」への答えは利用者に関しては既に実証済みである。

他方、流布する「15分でAIセカンドブレイン完成・コーディング不要」は初心者向けの煽りである。15分で到達できるのはエージェントをVaultに接続する初期接続までで、研究・論文執筆に耐える運用には、原資料のimmutable化、CLAUDE.mdによる規律、git管理、Lint、典拠検証、破壊的編集の防止が要る。とりわけ法学博士論文では、生成要約を「知識」として扱う前に、一次資料・脚注・判例・条文への戻り道を固定する必要がある。

中心命題：Karpathy式LLM Wikiは RAGの代替ではなく、RAGの上に置く知識編集レイヤーである。生成Wikiは「論文本文」ではなく「出典付きの編集済み研究台帳」として扱う限りにおいて、長期研究に対して複利的な価値を持つ。Wikiを最終証拠にした瞬間に、それは劣化したRAGに転落する。

IIアーキテクチャの解剖 ― RAG と LLM Wiki

RAGは基本的に、query時に文書をchunk検索し、関連断片をLLMに渡してその場限りの回答を生成する。強いのは大量文書からの探索・未整理資料への即時アクセス・意味検索・出典付きQAである。弱いのは、同じ統合・比較・矛盾処理を毎回やり直すこと、断片検索が外れると回答品質が崩れること、長期的な理解が蓄積しにくいことである。

Karpathy式は、生資料を検索対象にするだけでなく、LLMが中間生成物として Wiki を作る。たとえば「岡村忠生CFC論文」「Avi-Yonah実質主義」「TK匿名組合のD/NI問題」「2025年改正の矛盾」などを概念ページ化し、相互参照し、後続資料で更新する。したがってquery時には、原文断片だけでなく 既に編集された研究地図 に対して質問できる。

優れる場面／劣る場面

優れる場面劣る場面
長期研究・博士論文・書籍執筆・判例体系化など、同じ論点を何度も再利用する場合最新ニュース・膨大な法令全文・判例全文DBなど、毎回一次ソース全体から検索したい場合
「A論文とB判決の緊張関係」「過去の自分の問題意識の変遷」など、単純検索より統合が重要な場合典拠完全性が必要で、LLM要約を中間層に置くこと自体がリスクになる場合
人間が読むObsidianグラフ・LLMが読むMarkdown・git差分が同一資産になる場合数千〜数万文書で、grepや全文走査では候補集合を絞れない場合
回答そのものを新規ノートとして還元し、次回以降の素材にできる場合生成Wikiが肥大化し、誤要約や古い主張が残留する場合

grep／全文走査 vs 埋め込み検索

方式強い弱い
grep / rg法令名・条文番号・事件名・著者名・専門用語。再現性が高く、日本語の固有語・条番号検索に非常に強い言い換え・概念類似・暗黙関係を拾いにくい
埋め込み検索「CFCの法人格否認的把握に近い議論」のような意味検索条文番号・脚注番号の厳密一致、否定表現、時系列、細かい法的限定に弱い
最適解：法学用途では、まずWikiで概念地図を持ち、候補探索はChromaDB／全文検索、最終確認は一次資料。Wikiだけで結論を出さない。

IVCLAUDE.md（schema）の設計とテンプレ

良い CLAUDE.md は知識を詰め込むファイルではなく、編集規律・フォルダ役割・ワークフロー・禁止事項・検証手順を書くファイルである。なお CLAUDE.md はセッション開始時に文脈として読み込まれるが、それ自体は権限制御ではない点に注意を要する7。以下は /home/user/OCC_Vault/CLAUDE.md にそのまま貼れる骨子である。

# OCC Vault LLM Wiki Schema

## Mission
法学・税務の博士論文（日本CFC税制）のための知識基盤。
不変の生資料と利用者の間に、永続Markdown Wikiを維持する。
生成ノートを一次的権威として扱わない。

## Directory Roles
00_Inbox/      : 未処理の調査依頼・ノート
10_Processing/ : 進行中分析の作業領域
20_Projects/   : 完成済プロジェクト出力・長文レポート
30_Templates/  : 再利用テンプレ（指示なき限り変更しない）
40_Knowledge/  : 安定した統合知識エントリ（canonical）
50_Connections/: 横断マップ・矛盾マップ・論証依存グラフ
60_System/     : システム指示・索引・ログ・lint報告
70_Analytics/  : 指標・利用分析

## Source Authority Rules
1. 一次資料・条文・判例・PDF・引用脚注は immutable。
2. 原文テキストを書き換えない。
3. 引用・脚注番号・事件名・条番号・年月日・頁を、
   利用者の明示指示かつ原典再確認なしに改変しない。
4. 生成主張は次のいずれかで status 明示：
   source-confirmed / inference / hypothesis / needs-verification
5. 法的結論には、生資料・プロジェクト報告・RAG/判例DB結果への
   source trail（戻り道）を必ず付す。

## Note Frontmatter (YAML)
type: knowledge|connection|case|statute|literature|question|lint
status: draft|reviewed|source-confirmed|deprecated
topic / jurisdiction / source_refs / related / created / updated

## Ingest Workflow
資料種別と権威レベルを判定 → 読込 → 安定価値がある時のみ
40_Knowledge に短い要約を作成/更新 → 概念頁を更新 →
関係が変わる時 50_Connections を更新 → 不一致・不確実は
潰さず保持 → [[backlink]] 付与 → 未検証統合は needs-verification。

## Query Workflow
40_Knowledge と 50_Connections を先に検索 → 20_Projects を検索 →
不足時のみ外部RAG/判例/条文DBで一次確認 → 再利用可能な洞察は
canonical note を更新（重複ノートを作らない）。

## Lint Workflow（修正せず報告のみ）
リンク切れ / 孤立ノート / 30日超の needs-verification /
同一条文・判例・学説・改正に関する矛盾 / source_refs 欠落 /
過長ノート / 一次source trail なき生成主張
→ 60_System/lint/ に報告。

## Editing Safety
広範編集前に git status 確認 → 小さく差分可読に →
安定ノートの一括編集は5本まで（超は要確認）→
明示承認なき削除禁止 → 全書換でなく append/section 更新。
設計思想：このschemaの肝は「Source Authority Rules」第3〜5項。脚注・条番号・年月日を生成補完させない・source_refsを必須にする——この一点が、利用者がメモに何度も残してきた「ハルシネ典拠」事故を構造的に防ぐ。

Vスケーリングと限界

実機確認した利用者のVaultは84 Markdown。現時点ではKarpathy式に非常に向いており、rgで十分走査でき、40・50を整備すればLLMが全体像を把握しやすい。

規模挙動と必要対応
数百ノートまだgrep中心で運用可。CLAUDE.mdを短くし詳細規則は 60_System/rules/ に分割。50_Connections に論点別マップを作ると探索コストが下がる
数千ノート毎回Vault全体を読むのは不可能。rg検索語が悪いと重要ノートを落とす。同名概念・古い・重複・deprecatedが増える。Lintが必須・RAG併用が現実的

ベクトルRAG併用が必要になる兆候は、(1)「この概念に似た議論を全部探して」が増える、(2) raw sourceが数千〜数万単位、(3) 同義語・翻訳語・英日対応が多い、(4) Wikiが答えを持たないがraw corpusにはありそう、(5) 反対説・少数説・脚注レベルの拾い漏れが問題になる、の各場合である。法学用途では Wiki＝研究判断の作業机、ChromaDB＝探索エンジン、判例DB/法令DB/PDF＝証拠保管庫 と分けるのがよい。

VI失敗モードとリスク緩和

失敗モードリスク緩和策
原文改変LLMが原資料・引用文を「読みやすく」直すraw sourcesは raw/ またはVault外でread-only。引用ノート編集禁止。git差分監査
ハルシネ混入存在しない判例・論文・条文趣旨をWikiに混ぜるfrontmatterに status: needs-verification 強制。source_refs なき法的結論をLintで検出
相互参照の
誤接続		似た概念を誤リンク（例：CFCの経済活動基準とPillar 2 substance carve-out を過度に接続）50_Connections に関係タイプを記す：supports / contradicts / analogous / not_same_as を区別
無限肥大query回答を全部note化し低品質ノートが増殖note作成基準（再利用可能な洞察のみ・canonical更新優先・月次でdeprecated）
プライバシーVault外の機微ファイルを読む。会話履歴のローカル平文保存4Vault専用起動・許可ディレクトリ限定・.env等deny・履歴削除方針
破壊的編集一括rename・delete・全ファイル整形git・pre-commit・削除禁止・安定ノート5本超は確認制・hooks

VIII利用者固有の最適化 ― OCC_Vault × ChromaDB

実機確認したVaultは84mdで 00_Inbox / 10_Processing / 20_Projects / 30_Templates / 40_Knowledge / 50_Connections / 60_System / 70_Analytics の10桁分類を既に備える。これはKarpathy式を新設するより、既存OCC_VaultをKarpathy式として解釈し直すのが最適である。

役割実体（利用者の資産）
Raw sourcesVault外または 20_Projects 配下の原成果物・判例DB・PDF・法令DB・ChromaDB元文書。原則immutable
Wiki40_Knowledge（概念・学説・判例・制度・比較法のcanonical note）＋ 50_Connections（論証関係を書く相互参照層）
SchemaCLAUDE.md ＋ 60_System/rules/ ＋ lint reports

ChromaDB RAGとの役割分担

ChromaDB＝raw corpus探索・類似論点発見・判例/論文候補抽出。Wiki＝抽出後の研究判断・統合・矛盾管理・章立て接続。判例DB＝事案・判旨・裁判年月日・出典の一次確認。LLM Wikiは「この論文で使える形」に加工された、ただし出典付きの中間知識に徹する。

50_Connections を論証グラフに育てる（最重要）

単なるリンク集でなく論証関係を書く。実機確認では 50_Connections は現在2サブフォルダのみで中身が薄く、育てる余地が最も大きい層である。例：

図2　50_Connections に作るべき接続マップ例

50_Connections/CFC_Thesis/
  ├─ CFC博士論文_中核論点マップ.md
  ├─ CFC_法人格理論__岡村_渕_岡直樹_接続マップ.md
  ├─ TK匿名組合_DNI_CFC_比較法接続.md
  ├─ Pillar2_CFC_BEPS_Action3_緊張関係.md
  └─ 博士論文章立て_主張依存グラフ.md

各リンクに関係タイプを明示：[supports] [contradicts] [analogous] [not_same_as]
日本語法律文献の特有考慮：脚注番号・頁・判例年月日・裁判所・事件番号は絶対に生成補完しない。「示唆する／整合する／反する／同一ではない」を明示区別。法令は改正時点を持たせる。通達・裁判例・学説・私見を同じ権威レベルで並べない。source-confirmed と inference の区別が博士論文品質を左右する。

IX今夜の実装手順（実機検証・補正済）

実機検証で判明したCodex手順の誤り：Codexは別ディレクトリで実行されVaultの実状態を見ずに「git init で新規git化」と書いた。実際に確認すると gitルートは /home/user 全体（branch=master・コミット0件・未追跡1981ファイルの"事故repo"）が既に存在する。もし /home/user 階層で素朴に git add するとホーム全体の機微情報を巻き込む。対策＝OCC_Vault内に専用repoを切って分離する（下記で git init はVault内に .git を作るため安全かつ正しい）。
# 1. /home/user階層ではなくVault内に「専用repo」を切る
cd /home/user/OCC_Vault
git init                       # Vault内に.gitを作り独立repo化（親repoと分離）
printf '.obsidian/workspace*\n.trash/\n.DS_Store\n60_System/tmp/\n' > .gitignore
git add -A && git commit -m "Baseline: OCC vault 84 notes"

# 2. CLAUDE.md（§IVのschema）をroot配置 → immutable/脚注改変禁止/source_refs必須を明文化

# 3. Lint用ディレクトリ
mkdir -p 60_System/lint 60_System/rules

# 4. Claude Code を Vault root で起動（最初は調査のみ・編集禁止）
cd /home/user/OCC_Vault && claude

# 5. 50_Connections/CFC_Thesis/ に中核論点マップを1本だけ作る（一括再構成は禁止）
mkdir -p 50_Connections/CFC_Thesis

起動後に投げる初手プロンプト

CLAUDE.mdに従い、このVaultをKarpathy型LLM Wikiとして運用する準備をしたい。
まず編集せず、README.md・40_Knowledge・50_Connections の構造を調査し、
