要旨（ABSTRACT）

メタ研究の改善候補を、そのまま実装可能な計画へ落とした。各項目を現行コードに接地して設計し、fresh-contextの敵対的検証者が実コードを再読してpatchの正しさ・不変条件・churn判別を検査、完全性批評が構造的欠落を洗った。結果、素朴な「TIER1→TIER2」順は成り立たないことが判明——検証は4項目をneeds-pilotへ降格し(逐語照合器の素朴正典化は実データで検証済み559行の21%を誤降格)、完全性批評は4つの無主の土台(status→成果物ゲート/url解決上流化/ID連鎖スキーマ/観測先行)を発見した。ゆえに正しい順序は依存グラフに従う4フェーズで、観測基盤とスキーマを最初に置く。研究の中心結論「天井＝観測不能と非永続」を実装順序に翻訳したものである。

エグゼクティブサマリ

メタ研究は改善候補を洗い出したが、本プランはそれをそのまま実装可能な形にした——各項目を現行コードに接地して設計し、fresh-contextの敵対的検証者が実コードを再読して patch の正しさ・不変条件・churn判別を検査し、完全性批評が構造的欠落を洗った。その結果、素朴な「TIER1→TIER2」順は成り立たないことが判明した。

  • 敵対検証が4項目を needs-pilot へ降格した——いずれも「機構を足すが実害が未観測」または「上流化が検証済みコーパスを壊す」ため。特に逐語照合器の素朴な正典化は、実データで既存559 verifiedのうち430しか再現せず、118行(21%)を誤って未確証へ落とすことが実測された。
  • 完全性批評が4つの無主の土台を発見した——status→成果物の provenance ゲート／url解決の上流化／ID連鎖スキーマ（issue・from_signal・claim_id）／「未観測の欠陥を直す前に、その欠陥を観測する計器を置く」原則。

ゆえに正しい順序は依存グラフに従う4フェーズであり、観測基盤とスキーマを最初に置く。これは研究の中心結論「天井は観測不能と非永続」を実装順序に翻訳したものである。

完全性批評が明かした欠落（新規4項目）

  • G1 status→成果物の provenance ゲートが無主: quote-matcher は claim を hold/unverified へ降格するが、その status を成果物（HTML本文・脚注）から締め出す項が誰にもない。check_html は構造健全性(隣接sup・リンク)だけを見て、hold/unverified の claim が引用されていないかを検査しない。降格しても本文に残るなら降格は無意味。← 新規P1項目として追加。
  • G2 url→hold の解決者が集合内に不在: quote-matcher は run-local の curl取得+再照合能力を捨てurl を恒久holdにするが、取得を上流化する項がない。「run-local修理の上流化」という目的に反し、片割れを宙吊りにする。← quote-matcher項に url-fetch+再照合を内包。
  • G3 ID連鎖スキーマ（issue・from_signal・claim_id）が土台なのに未定義: journal-emit も calibration も signals→issue→ratchet の機械リンクを前提するが、issue イベント型も claim_id も正典に未定義。← Phase 0の最初に確立。
  • G4 未観測の条件を直す項が、その条件のプローブを足さない: runner-defects の FDリーク・torn read も、adaptive の rate_limit も239レーンで発現ゼロ。しかし kill失敗カウンタも torn検出器も設計にない。real か churn かを分ける観測手段が欠落。← 観測先行を Phase 0 に固定。
  • 追加note: check_html の credit-grep を fatal にすると正当な学術文書を過遮断（本セッションで実際に遭遇）→既定warn。

フェーズ別ロードマップ

Phase 0 — 基盤・観測（最優先・これ無しに他は測れない）

含む: G3スキーマ定義、emit.py+journal_view.py新設、runnerのコード発火(provenance/token完全性/cause_class/kill-counter)。 所要: 約10-14時間。 ゲート（次へ進む条件）: 実runを1本流し、journal_view が dry率・相別予算・較正率・hold寿命・cause_class集計を実データで出力すること。ここで初めて「FDリーク・torn・rate_limitは実際に起きるか」が測れる。 要点: provenance発火はcodex --versionをdispatch前に1回だけ（codex不在時null許容・dry-runをcrashさせない）。相別予算は verdict に lane_type が無いため EVENT_LANE_PLANNED/manifest と join。emit.py は1行CLIに保ち摩擦ゼロ（メタ劇場化＝主宰がemitを使わない罠の緩和）。

Phase 1 — 真の低リスク・即実施（Phase 0と並行可）

含む: shared-builder+check_html、svg-carveout、nest-runbook、mark_human_gate close、fsync。 所要: 約5-7時間。 ゲート: shared-builder は 20260708連結HTMLをFAIL・20260709の2件をPASSにする受入fixtureを通すこと。薄いラッパ化(フォーク削除)は keiri/hikakuho 双方で byte-identical diff を確認してから。 要点: check_html は既定warn(--strictでfatal)。mark_human_gate close は冪等・実質無リスクだが発火実績は未観測(集中版:1066推奨・限定版:952/1000直書きは避ける)。

Phase 2 — 上流化・成果物ゲート（Phase 0のスキーマ・観測に依存）

含む: quote-matcher(3是正+url-fetch)、G1 status→成果物ゲート、calibration ARM(c) view生成器。 所要: 約8-12時間。 ゲート: quote-matcher は検証済み559行を無損失で再現する fixture を通すこと（素朴版は430=21%損失。segment語彙一致・全空白除去既定・gloss書換OFFの3是正必須）。G1ゲートは build_html/check_html が hold/unverified の claim を本文引用していないか検査し、あれば公開失敗。 要点: url解決は run-local の curl取得+再照合を verify_quotes.py へ内包（宙吊りにしない）。gloss→claim の quote列書換は既定OFF(--gloss-splitで任意)＝逐語列は非可逆改変しない。

Phase 3 — pilot・測ってから採る（Phase 0観測が条件実在を示した場合のみ）

含む: 原子公開+orphan回収、adaptive並列2-3層、calibration対照試験ARM(a)(b)。 所要: 各pilotで可変（測定期間依存）。 ゲート: 採用の前提は Phase 0観測の集計が「その条件が実際に起きる」ことを示すこと。runnerは239レーンで終端失敗0なので、証拠が出るまで採用しない（無条件採用＝churn）。原子公開は orphan .pending 回収経路(起動時に孤児pendingをnonce判定して公開)を同伴させること。
