3. 深堀り (1): Subagent活用

Subagentとは何か

Subagentは、メインのClaude Codeセッションから独立したコンテキストウィンドウを持つ別のClaudeインスタンスを生成する仕組みである。Vishwasはこれを「specialist agents you define that your main agent can spawn to do focused, isolated work and report back with the result」（メインエージェントが生成できる、集中的かつ隔離された作業を行う専門エージェント）と定義している。

なぜSubagentが必要か -- コンテキスト汚染問題

Claude Codeの全てのベストプラクティスは一つの制約に基づいている：コンテキストウィンドウは有限であり、埋まるほど性能が劣化する。15分の探索的作業の後、メインスレッドには400行以上のログが蓄積される。Subagentはこの「コンテキスト汚染」を区画化する。調査のノイズはSubagent内に封じ込められ、メインエージェントには最終結果のみが返される。

Subagentの3つの能力

  • 並列実行 -- 複数の専門エージェントを同時に実行し、それぞれが独立した200Kトークンのコンテキストを持つ
  • ツールスコーピング -- エージェントごとに異なるツールへのアクセスを制御。例: コードレビュー用は読み取り専用、テスト実行用はBash実行可能
  • モデルミキシング -- タスクに応じて異なるLLMを使い分ける

実装方法

カスタムSubagentは.claude/agents/ディレクトリにMarkdownファイルとして定義する:

---
name: code-reviewer
description: Reviews code for style and correctness
model: sonnet
tools:
  - Read
  - Grep
  - Glob
isolation: worktree
---

Review the provided code changes for:
- Style consistency
- Potential bugs
- Performance issues

Return a structured review with severity levels.

重要な制約

  • Subagentのコンテキストは完全に新規で始まる。親の会話は引き継がれず、Agentツールのプロンプト文字列だけが唯一の通信チャネル
  • Subagentは他のSubagentを生成できない。ネスト委譲が必要な場合は、Skillsを使うか、メイン会話からSubagentをチェーンする
  • isolation: worktreeを設定すると、リポジトリの隔離コピーで動作し、ファイル競合を防止できる

ユースケースパターン

パターン説明利点
探索委譲ファイル調査やログ解析をSubagentに委託メインコンテキストを汚さない
並列レビュー複数ファイルを同時にレビュー時間短縮
テスト実行テストスイートの実行と結果分析テスト出力がメインを汚染しない
リファクタリングworktree隔離でリファクタリングを試行失敗時に安全にロールバック

4. 深堀り (2): --worktree による並列開発

Boris Cherny（Claude Code開発者）の証言

Claude Codeを構築したBoris Cherny自身が、3-5個のgit worktreeを同時に立ち上げることを「the single biggest productivity unlock」（最大の生産性向上策）と明言している。Claude Codeチームの多くのメンバーがworktreeを好み、これがDesktopアプリとCLIの両方でネイティブサポートが実装された理由である。

Git Worktreeの基本原理

Git worktreeは、同一リポジトリの履歴とリモート接続を共有しながら、それぞれが独立したファイルシステムとブランチを持つ別の作業ディレクトリを作成する仕組みである。つまり、worktree Aでfeature-authを開発しながら、worktree Bでbugfixを進められ、互いに干渉しない。

使い方

# worktreeを作成してClaudeを起動（ブランチ名 = ディレクトリ名）
claude --worktree feature-auth
# 短縮形
claude -w feature-auth

# 複数ターミナルで同時に起動
# Terminal 1:
claude -w feature-auth
# Terminal 2:
claude -w bugfix-login
# Terminal 3:
claude -w refactor-api

生産性3-5倍の仕組み

生産性向上のメカニズムは単純明快である:

  1. 待ち時間の排除 -- Claude がworktree Aで実装中に、worktree Bでレビューし、worktree Cで次の問題を議論できる
  2. コンテキスト分離 -- 各worktreeのClaudeは独立したコンテキストを持つため、タスク切り替えのオーバーヘッドがゼロ
  3. 安全な並列実験 -- 失敗しても他のworktreeに影響しない。gitの安全性がそのまま適用される

ライフサイクル管理

worktreeセッション終了時の動作:

  • 変更なし -- worktreeとブランチが自動的に削除される
  • 変更あり -- Claudeが「keep or remove?」とプロンプトを出し、ユーザーが選択する

高度な活用: WorktreeCreate / WorktreeRemove Hooks

worktree作成・削除時に発火するフックを設定できる。これにより:

  • gitignoreされたファイルを.worktreeinclude経由でコピー
  • ブランチ名からユニークなDB名を導出した.env.localを自動生成
  • bin/setupを自動実行して環境構築を完了
  • Git以外のVCS（SVN、Perforce、Mercurial）でもカスタムworktreeロジックを提供可能

実践的ワークフロー例

# 朝のルーティン: 3つのworktreeを立ち上げ
claude -w feat/user-dashboard    # 新機能開発
claude -w fix/memory-leak        # バグ修正
claude -w chore/deps-update      # 依存関係更新

# シェルエイリアスでワンキー切り替え
alias cw1='cd ~/project/.worktrees/feat-user-dashboard'
alias cw2='cd ~/project/.worktrees/fix-memory-leak'
alias cw3='cd ~/project/.worktrees/chore-deps-update'

5. 深堀り (3): Hooks -- ライフサイクルへの介入

Hooksの本質

HooksはClaude Codeのライフサイクルの各ポイントで実行されるシェルコマンドである。「受動的な監視」ではなく、ツール実行の許可・拒否・変換を能動的に制御できる。Vishwasは特にPostToolUseでの自動フォーマットとPreToolUseでの危険コマンドブロックを重点的に解説している。

フックの種類

フック名発火タイミング主な用途
PreToolUseツールパラメータ作成後、実行前ポリシーガード、危険コマンド遮断
PostToolUseツール実行完了直後自動フォーマット、クリーンアップ
Notification通知送信時compaction後のコンテキスト再注入
UserPromptSubmitユーザーがプロンプト送信時入力バリデーション
Stopメインエージェント終了時後処理、ログ記録
SubagentStopSubagent終了時Subagent結果の加工
WorktreeCreateworktree作成時環境構築の自動化
WorktreeRemoveworktree削除時クリーンアップ
SessionEndセッション終了時最終処理

PostToolUse: 自動フォーマットの設定例

.claude/settings.jsonに以下を追加:

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "command": "npx prettier --write \"$CLAUDE_FILE_PATH\" 2>/dev/null || true"
      },
      {
        "matcher": "Edit|Write",
        "command": "npx eslint --fix \"$CLAUDE_FILE_PATH\" 2>/dev/null || true"
      }
    ]
  }
}

ポイント:

  • matcherでEdit/Writeツールのみに限定（Read等では発火しない）
  • || trueでフォーマッタのエラーがClaudeの動作をブロックしないようにする
  • Prettier → ESLintの順でチェーンし、フォーマット → lint修正の2段階を自動化
  • $CLAUDE_FILE_PATH環境変数で編集対象ファイルのパスを受け取る

PreToolUse: 危険コマンドのブロック

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "command": "echo '$CLAUDE_TOOL_INPUT' | jq -r '.command' | grep -qiE 'rm\\s+-rf|drop\\s+table|truncate' && echo 'DENY: Dangerous command blocked' && exit 1 || exit 0"
      }
    ]
  }
}

PreToolUseはツール実行前に発火するため、破壊的コマンドが実行される前に遮断できる。exit 1を返すとツール実行が拒否される。

設計原則

Vishwasの推奨: PreToolUseはポリシーガード（何を許可/拒否するか）に、PostToolUseはクリーンアップとフィードバック（実行後の自動処理）に使い分ける。また、対話的な/hooksコマンドでメニューから設定することもでき、JSONを直接編集するより簡単な場合がある。

6. 深堀り (4): Plan Mode -- 設計と実装の分離

Plan Modeの基本概念

Plan ModeはClaude Codeの3つの権限モード（Normal / Auto-accept / Plan）の一つで、Claudeに「考えさせるが実行させない」モードである。Shift+Tabで会話を中断することなく即座に切り替えられる。

いつPlan Modeを使うべきか

Vishwasは明確な基準を示している:

  • 使うべき場面: マルチファイル変更、不慣れなコードベース、アーキテクチャ決定
  • スキップすべき場面: 小さなスコープのタスク。「diffを一文で説明できるなら、直接やれ」

Plan Modeのオーバーヘッドは数分程度だが、これにより「Claudeが20分かけて自信満々に間違った問題を解く」事態を防止できる。

3つのモードの使い分け

モード動作適用場面
Normal各ツール実行時に承認を求める通常作業。安全だが手動承認が多い
Auto-accept全てのツール実行を自動承認信頼できるタスク。手放し運転
Plan設計・分析のみ。ファイル変更しない設計レビュー、方針策定、調査

効果的なPlan Mode活用ワークフロー

  1. Plan Modeで開始 -- 「このコードベースで認証機能を追加するベストな方法は?」と質問。Claudeが既存コードを調査し、設計案を提示する
  2. 設計をレビュー -- Claudeの提案を人間がレビュー。修正指示があればPlan Modeのまま議論を続ける
  3. Shift+TabでNormalに切替 -- 設計が固まったら実装モードに移行。「さっき議論した設計案を実装して」と指示
  4. 必要に応じてPlanに戻る -- 実装中に予想外の問題が出たら、再びPlanに切り替えて方針を再検討

Plan ModeとSubagentの連携

Plan Modeで設計した後、実装をSubagentに委譲するのが高度なパターンである。メインセッションは設計と監督に集中し、各実装タスクは隔離されたSubagentが担当する。これにより、メインのコンテキストは「設計の意図」のみを保持し、実装の詳細で汚染されない。

7. 深堀り (5): Compaction対策 -- 長時間セッションの生命線

Compactionとは何か

Compactionは、コンテキストウィンドウが一定の閾値に達した際にClaude Codeが自動的に会話を要約・圧縮する仕組みである。デフォルトではコンテキストの95%が埋まった時点で発動する。圧縮により会話は続行できるが、重要な詳細が失われるリスクがある。

Vishwasの2段階戦略

戦略1: 閾値の前倒し

デフォルトの95%ではなく、75%でcompactionを発動させることを推奨。これにより、性能劣化が始まる前に圧縮が実行される:

# 環境変数で設定
export CLAUDE_CODE_AUTO_COMPACT_WINDOW=75
# または
export CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=75

戦略2: Notificationフックでコンテキスト再注入

compaction発動時に自動的に重要情報を再注入する仕組みを構築する。これが長時間セッションでの最も価値あるテクニックとされる:

{
  "hooks": {
    "Notification": [
      {
        "matcher": "compact",
        "command": "cat ~/.claude/reinject-context.md"
      }
    ]
  }
}

reinject-context.mdに記載すべき内容:

  • 現在のタスク記述 -- 「何をやっているか」の明確な定義
  • 変更済みファイル一覧 -- セッション中に編集したファイルのリスト
  • ハード制約 -- 「migrationファイルは変更禁止」等の絶対ルール
  • テスト状況 -- 現在のテスト通過/失敗状況

手動Compactionの活用

/compactコマンドに焦点指示を付けることで、何を保持すべきかをClaudeに明示できる:

/compact Focus on the API changes and the list of modified files

また、CLAUDE.mdに常設の指示を追加する方法もある:

## Compaction Rules
When compacting, always preserve:
- The full list of modified files
- Current test status (pass/fail counts)
- Active task description and acceptance criteria

メモリ管理の全体戦略

  1. /clear の積極的使用 -- 無関係なタスク間では必ずコンテキストをクリア。バグ修正後に新機能を始めるなら、古いコンテキストは「積極的に害がある」
  2. 遅延ロード -- 全ファイルを事前に読み込ませず、必要時に参照させる
  3. セッション終了前の永続化 -- #記号で即座にメモリに保存。「always use MUI components for new stuff」のようなルールを蓄積
  4. Compaction閾値の前倒し -- 75%で早めに圧縮
  5. Notificationフック -- 圧縮時に重要情報を自動再注入
核心的な洞察: Vishwasの全てのTipsは一つの制約に帰着する -- 「Claudeのコンテキストウィンドウは有限であり、埋まるほど性能が劣化する」。50個のTipsの大半は、この制約をいかに管理するかという問題の異なる側面を扱っている。Compaction対策はその中でも最も直接的な対処法である。

8. その他の注目Tips詳細

ccエイリアスの設定

# ~/.zshrc または ~/.bashrc に追加
alias cc='claude --dangerously-skip-permissions'
alias ccp='claude --plan'          # Plan Mode直接起動
alias ccr='claude --resume'        # セッション復帰

!プレフィックスでBash即時実行

!git status や !npm test で即座にコマンドを実行。出力はコンテキストに残るため、Claudeがその結果を見て応答できる。

Ctrl+S でドラフト退避

長いプロンプトを書いている途中で急ぎの質問がある場合、Ctrl+Sでドラフトを退避。質問を送信後、退避したドラフトが自動的に復元される。

Ctrl+B でバックグラウンド実行

長時間のBashコマンド実行中にCtrl+Bでバックグラウンドに送り、Claudeとの対話を継続できる。

LSPプラグイン

Vishwasが「the single highest-impact plugin」と評するLSP連携。go-to-definition、find-references、hover info、symbol searchなどのIDE機能をClaude Codeに統合する。~/.claude/CLAUDE.mdに「Prefer LSP for code navigation」と記載することで、Claudeがgrepの代わりにLSPを使うようになる。

カスタムSlash Commands

# .claude/commands/review.md の内容例:
Review the changes in $ARGUMENTS for:
- Code style consistency
- Potential bugs
- Test coverage gaps
Return a structured review.

/review src/auth/のように使用する。

/install-github-app

GitHub Appをインストールして、Claudeに自動的にPRレビューさせる設定。CI/CDパイプラインとの統合も可能。

9. Vishwas流 -- 実務ワークフロー提案

朝のセッション開始ルーティン

  1. 3-5個のworktreeを立ち上げ（機能開発、バグ修正、依存関係更新など）
  2. 各worktreeでClaude Codeを起動し、Plan Modeで設計を開始
  3. 設計が固まったworktreeからAuto-acceptモードに切り替えて実装開始
  4. 実装中のworktreeを監視しつつ、別のworktreeでレビュー

長時間セッションの管理

  1. compaction閾値を75%に設定
  2. Notificationフックで重要コンテキストの自動再注入を設定
  3. タスク切り替え時は/clearを必ず実行
  4. セッション終了前に#で重要な学びをメモリに保存

安全性の確保

  1. PreToolUseフックで危険コマンドをブロック
  2. PostToolUseフックでPrettier/ESLintを自動実行
  3. CLAUDE.mdに検証コマンド（test/build/lint）を必ず記載
  4. 大きな変更前にはgit commitで安全ネットを張る

10. 他の3人の思想家との関連性

Boris Cherny（Claude Code開発者）との関係

Vishwasの50 Tipsは、Boris Chernyの設計思想を最も忠実に体系化したものである。Boris自身が「3-5 worktreeの並列実行が最大の生産性向上策」と述べた知見が、Vishwasの並列ワークフローセクションの基盤となっている。VishwasはBorisの「コンテキストエンジニアリング」哲学を実践的なTipsに翻訳する役割を果たしている。

Steve Sewell（Builder.io CEO）との関係

同じBuilder.ioに所属するSteve Sewellは「Claude Code First」のワークフローシフトを提唱した。Vishwasの記事はSewellの実践をより構造化・体系化したものと位置づけられる。SewellがVS Code拡張からの移行経験を語る一方、Vishwasはその先の最適化テクニックを50項目に凝縮している。

John Kim（Push to Prod）との関係

John Kimは同じ50 Tipsを自身のSubstackで紹介・解説しており、「Claude Code is fundamentally a context engineering tool」（Claude Codeは本質的にコンテキストエンジニアリングツール）というVishwasの核心テーゼを強化している。KimはさらにAgent Teamsに関する30 Tipsも執筆しており、VishwasのSubagent解説の延長線上にある。

共通する核心思想

これら4者に共通するのは「コンテキストが王」（Context is King）という認識である。プロンプトの巧みさよりも、Claudeに何を見せ何を隠すかの設計が成果を決定する。Vishwasの50 Tipsは、この原則をFoundations（基盤）→ Shortcuts（操作）→ Commands（制御）→ CLAUDE.md（設定）→ Workflow（運用）→ Composability（構成）→ Parallel（並列）→ Hooks（自動化）→ Philosophy（哲学）という美しい階層で展開しており、単なるTips集を超えた「Claude Code運用の体系的フレームワーク」となっている。
