Workflowツール 完全図解マニュアル

決定論的マルチエージェント・オーケストレーション — Claude Code組み込みツール
底本: システムプロンプト内ツール定義（英語原文）の全文転写 ~/.claude/WORKFLOW_TOOL_MANUAL.md ／ 転写日 2026-07-05

Workflowツールは、制御フローをLLMではなくJavaScriptスクリプトが握るマルチエージェント実行機構である。 ループ・分岐・ファンアウトが決定論的に走り、途中停止からのレジューム（キャッシュ再生）を内蔵する。 本書はツール定義の全記述 — 起動ゲート、スクリプト仕様、API 8種、並列モデル、品質パターン7種、レジューム機構、全制約値 — を 12枚のSVG図解と参照表に写像したものである。図中の数値・挙動はすべて原文の記述に基づき、推測による補完はない。

検証注記：本書の範囲は「ツール定義に書かれていること」に限る。/workflows 画面のUI詳細、課金、内部実装などは原文に記述がないため扱わない。原文と突き合わせる場合は上記転写ファイルを参照。

§1 全体アーキテクチャ

呼び出すと即座にタスクIDが返り、本体はバックグラウンドで走る。メインループは待たずに次の作業へ移れる。完了は <task-notification> で届き、進行中は /workflows でライブ監視できる。

ワークフローの存在意義は3つ — 網羅（分解して並列にカバー）、確信（独立視点と敵対的検証を経てからコミット）、規模（1コンテキストに収まらない移行・監査・横断調査）。スクリプトは「何をファンアウトし、何を検証し、何を統合するか」の構造をコード化する場所である。

§2 起動ゲート — 明示オプトイン必須

数十体のエージェントと大量トークンを消費し得るため、規模はユーザーが請求するものであって推定するものではない。以下5条件のいずれかが成立しない限り、Claudeはこのツールを呼んではならない。

§3 スクリプトの解剖 — meta純リテラル契約と実行環境

すべてのスクリプトは export const meta = {...} で始まらなければならない。metaは純リテラル（変数・関数呼出し・スプレッド・テンプレート補間の一切を禁止）。本体はトップレベルawaitが使えるasync文脈のplain JavaScriptである。

§4 agent(prompt, opts) — 全オプション図解

1体のサブエージェントを起動する最小単位。戻り値は3通り、オプションは7種。model / effort は省略が最良の既定（セッション設定を継承する）である点が繰り返し強調されている。

§5 pipeline() vs parallel() — バリアの実コストをタイムラインで見る

原文が最も紙幅を割く論点。既定はpipeline。parallelは「全結果を同時に必要とする」ことを証明できたときだけ使うバリア（同期壁）である。下図は探索段の所要が A=180／B=300／C=540、検証段が各160の場合の実時間比較。

§6 バリア正当化テスト — smell test付き

バリア（parallelによる同期壁）が許されるのは「段Nが段N−1の全体を必要とする」場合だけ。原文は正当化される3ケースと、正当化にならない3つの言い訳を明示的に列挙している。

§7 schema — 構造化出力の強制と自動リトライ

optsにJSON Schemaを渡すと、サブエージェントはStructuredOutputツールの呼出しを強制される。検証はツールコール層で行われるため、型不一致はモデル自身が再試行する — スクリプト側にパース・検証コードは一切不要。

§8 budget — ターン全体で共有されるトークンプール

ユーザーの「+500k」型指示がターンの目標トークン量になる。プールはメインループ＋全ワークフロー共有であり、上限は助言ではなく強制 — 超過後のagent()はthrowする。

§9 workflow() — 入れ子実行は1段まで

保存済みワークフローや別スクリプトを、実行中のワークフロー内から子として呼べる。子は親の実行資源（同時実行枠・agentカウンタ・abortシグナル・トークン予算）を共有する — 独立した財布を持たない。

§10 品質パターン① 検証系 — 見つけた主張を疑う構造

「もっともらしいが誤り（plausible-but-wrong）」の発見を生き残らせないための3パターン。CFC論文運用でのスワーム校閲（指摘も修正案も一次資料照合）と同じ思想が、ここではスクリプト構造として強制される。

§11 品質パターン② 探索系 — 「全部見つけた」を構造で担保する

発見タスクの敵は「早すぎる打ち切り」と「無言の切り詰め」。件数カウンタではなく乾き（dry）で終了を判定し、絞った範囲は必ずlog()で開示する。

原文の結び：「これらのパターンは網羅列挙ではない — タスクが求めるなら新しいハーネスを構成せよ（トーナメント方式、自己修復ループ、段階的エスカレーション等）」。部品庫と選択判断で毎回設計する/flawの思想と同じ構えである。

§12 Resume機構 — 最長不変プレフィックスのキャッシュ再生

停止・強制終了・スクリプト編集後、resumeFromRunId で再投入すると、変更されていない先頭からのagent()呼出し列はキャッシュから即時に結果を返し、最初の変更点以降だけがライブ実行される。Date.now()等の禁止はこの機構の代償である。

§13 注釈付きコード例全集（原文の5例）

例1 — canonical：pipeline＋段内parallel（次元別レビュー→発見即検証）

export const meta = {
  name: 'review-changes',
  description: 'Review changed files across dimensions, verify each finding',
  phases: [{ title: 'Review' }, { title: 'Verify' }],
}
const DIMENSIONS = [{key: 'bugs', prompt: '...'}, {key: 'perf', prompt: '...'}]
const results = await pipeline(
  DIMENSIONS,
  d => agent(d.prompt, {label: `review:${d.key}`, phase: 'Review', schema: FINDINGS_SCHEMA}),
  review => parallel(review.findings.map(f => () =>
    agent(`Adversarially verify: ${f.title}`, {label: `verify:${f.file}`, phase: 'Verify', schema: VERDICT_SCHEMA})
      .then(v => ({...f, verdict: v}))
  ))
)
const confirmed = results.flat().filter(Boolean).filter(f => f.verdict?.isReal)
return { confirmed }
// bugs次元の検証は、perf次元がまだレビュー中でも走る — 実時間のムダなし
// 注釈：段内のparallelは「1 findingのN検証待ち」であってステージ間バリアではない。
// phaseはopts側で明示（pipeline内でグローバルphase()を呼ぶとレースする — §4）

例2 — バリアが正しい例：全発見をdedupしてから高価な検証へ

const all = await parallel(DIMENSIONS.map(d => () => agent(d.prompt, {schema: FINDINGS_SCHEMA})))
const deduped = dedupeByFileAndLine(all.filter(Boolean).flatMap(r => r.findings))  // ← 全体を同時に必要とする＝バリア正当
const verified = await parallel(deduped.map(f => () => agent(verifyPrompt(f), {schema: VERDICT_SCHEMA})))
// 注釈：dedupは「アイテム横断依存」の典型 — §6の正当化ケース①に該当

例3 — loop-until-count と loop-until-budget

// 件数目標型
const bugs = []
while (bugs.length < 10) {
  const result = await agent("Find bugs in this codebase.", {schema: BUGS_SCHEMA})
  bugs.push(...result.bugs)
  log(`${bugs.length}/10 found`)
}

// 予算消化型 — budget.totalガードが無いとremaining()=Infinityで1000体上限まで暴走
while (budget.total && budget.remaining() > 50_000) {
  const result = await agent("Find bugs in this codebase.", {schema: BUGS_SCHEMA})
  bugs.push(...result.bugs)
  log(`${bugs.length} found, ${Math.round(budget.remaining()/1000)}k remaining`)
}

例4 — 複合：exhaustive review（find→seen対比dedup→多レンズ審査→loop-until-dry）

const seen = new Set(), confirmed = []
let dry = 0
while (dry < 2) {                                             // loop-until-dry
  const found = (await parallel(FINDERS.map(f => () =>         // バリア：ラウンドの全finderを収集（正当）
    agent(f.prompt, {phase: 'Find', schema: BUGS})))).filter(Boolean).flatMap(r => r.bugs)
  const fresh = found.filter(b => !seen.has(key(b)))          // seen対比dedup — プレーンコードで（agentでない）
  if (!fresh.length) { dry++; continue }
  dry = 0; fresh.forEach(b => seen.add(key(b)))
  const judged = await parallel(fresh.map(b => () =>           // 新規バグ全件を同時審査…
    parallel(['correctness','security','repro'].map(lens => () =>  // …各3レンズで
      agent(`Judge "${b.desc}" via the ${lens} lens — real?`, {phase: 'Verify', schema: VERDICT})))
      .then(vs => ({ b, real: vs.filter(Boolean).filter(v => v.real).length >= 2 }))))
  confirmed.push(...judged.filter(v => v.real).map(v => v.b))
}
return confirmed
// dedupはconfirmedでなく「seen」と比較 — さもないと審査棄却分が毎ラウンド再出現し永久に収束しない

例5 — Adversarial verify（多数決の骨格）

const votes = await parallel(Array.from({length: 3}, () => () =>
  agent(`Try to refute: ${claim}. Default to refuted=true if uncertain.`, {schema: VERDICT})))
const survives = votes.filter(Boolean).filter(v => !v.refuted).length >= 2
// 注釈：「不確実ならrefuted=true」— 立証責任を発見側に置く。生存には積極的な非反証が2票必要

§14 リファレンス表

14-1 ツールパラメータ

パラメータ型・制約説明
scriptstring ≤512KBインライン本体。冒頭にexport const meta必須。投入と同時にセッションdirへ自動保存され、パスが結果に返る
scriptPathstring優先度最高。自動保存されたファイルを編集して再投入する反復用
namestring定義済みワークフロー名（組込み or .claude/workflows/）を解決
argsanyスクリプト内グローバルargsにそのまま渡る。JSON値のまま渡す — 文字列化するとargs.map等がthrow
resumeFromRunId^wf_[a-z0-9-]{6,}$同一セッション内のみ。再開前に旧runをTaskStopで停止
title / descriptionstring無視される（metaブロックで設定する）

14-2 実行制約の全定数

制約値超過時の挙動
同時agent実行数min(16, CPUコア−2)／workflowキューイングされ枠が空き次第実行（エラーにならない）
生涯agent数1000体／workflow暴走ループのbackstop（実用ワークフローの遥か上に設定）
parallel/pipeline 1呼出しのアイテム数≤4096明示エラー（無言の切り詰めではない）
script引数サイズ≤512KB—
workflow()入れ子深度1段子の中の呼出しはthrow
Date.now() / Math.random() / 引数なしnew Date()使用不可throw（resume破壊防止）
TypeScript構文使用不可パースエラー
fs／Node.js API使用不可—（標準JSビルトインのみ）
budget超過後のagent()—throw（ハードシーリング）

14-3 null／エラー処理マトリクス

事象挙動呼出し側の作法
実行中にユーザーがagentをスキップそのagent()がnullに解決.filter(Boolean)を常用
リトライ後も恒久APIエラーそのagent()がnullに解決
parallel()のthunkがthrow該当要素がnull。呼出し自体は決してrejectしない結果配列を.filter(Boolean)してから使う
pipeline()の段がthrowそのアイテムがnull化・残段skip。他アイテムは続行最終結果で.filter(Boolean)
schema不一致ツールコール層で弾かれモデルが自動再試行関与不要
workflow()のname不明／scriptPath不可読／子構文エラーthrow劣化継続したければtry/catch
4096超のアイテム投入明示エラー分割する

14-4 定番の単相ワークフロー5類型（ターンをまたいで連鎖させる）

類型形
Understand関連サブシステムへ並列リーダー → 構造化マップ
DesignN独立アプローチのジャッジパネル → スコア付き統合
Review次元分解 → 発見 → 敵対的検証（§13例1）
Researchマルチモーダルスイープ → 深読み → 統合
Migrate対象サイト発見 → 各個変換（worktree隔離）→ 検証

大きな作業ではこれらを順に複数回実行し、各結果を自分で読んでから次の相を決める — 自分がループに残る。1ワークフロー＝1つの well-scoped なファンアウト。

14-5 swarm2 / codex-flow との位置づけ（参考・原文外）

観点Workflowツールswarm2 / codex-flow（既存運用）
実行主体ClaudeサブエージェントのみCodex exec（GPT-5.5 xhigh）が全実行
制御フローJSスクリプトによる決定論（組み込み）coordctl／runner.py（自作基盤）
レジュームrunIdキャッシュ再生を内蔵runner.pyの--resume／state.json
構造化出力schema＋ツールコール層検証（自動リトライ）「最後にJSONのみ」＋呼出し側検証（--output-schemaは既知の罠）
起動条件ユーザーの明示オプトイン必須/swarm2等のスキル起動

この行のみ本マニュアル外の比較情報（当環境の運用メモに基づく）。Codexを実行部隊にしたい場合は従来どおりswarm2／codex-flowが適役で、Workflowは「Claude系サブエージェントの決定論的統率＋レジューム」が欲しいときの選択肢。
