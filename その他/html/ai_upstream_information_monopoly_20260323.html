1.3 なぜ「一次情報」なのか

こはくの主張の核心は、AI情報が「伝言ゲーム」によって構造的に劣化するという指摘にある。この主張を検証するためには、まず情報伝達の各段階で何が失われるのかを理解する必要がある。

技術的な文脈で情報が翻訳・要約・再解釈される過程では、以下の要素が失われる:

  • 設計意図（Intent）: なぜその技術がそう設計されたかという哲学的背景
  • 制約条件（Constraints）: その設計判断に至った技術的・経済的制約
  • 失敗パターン（Anti-patterns）: 試行錯誤の過程で発見された「やってはいけないこと」
  • 暗黙知（Tacit Knowledge）: 言語化されにくいが実践者が共有する知識
  • 時間的文脈（Temporal Context）: その情報がいつの時点で正しかったかという時間軸

特にAIツールの進化速度を考えると、3〜6ヶ月の情報遅延は致命的である。2025年3月時点でClaude Codeにはhooksもworktreeもなかった。2025年9月にはsubagentが追加され、2026年初頭にはAgent Teamsが実装された。半年前の「ベストプラクティス」はもはや古い戦略である可能性が高い。

A.1 エージェント型AIコーディングツールの系譜

4人の海外ソースが語る内容を正しく理解するためには、2025-2026年のAI開発ツールのランドスケープを把握しておく必要がある。このセクションでは、Claude Codeを中心に、競合ツールとの比較、そしてエージェント型ツールが従来のコーディング補助ツールとどう異なるかを整理する。

第1世代: コード補完ツール（2021-2023）

GitHub Copilotに代表される第1世代のAIコーディングツールは、「コード補完」に特化していた。開発者がコードを書いている最中に次の行を予測し、提案する。これは本質的に「オートコンプリートの高度版」であり、開発者の作業フローを大きく変えるものではなかった。

  • 入力: 現在のファイルのコンテキスト + カーソル位置
  • 出力: 次の数行のコード提案
  • 人間の役割: コードの主導権を持ち、提案を承認/拒否する
  • コンテキスト: 現在のファイルと開いているタブ程度

第2世代: チャット型コーディング補助（2023-2024）

ChatGPT、Claude (チャット版)、GitHub Copilot Chatなどが登場し、自然言語でコーディングの質問をしたり、コードの生成を依頼したりできるようになった。しかし、これらは依然として「1ターンのQ&A」の域を出なかった。

  • 入力: 自然言語の質問 + コードの貼り付け
  • 出力: コードブロックのテキスト回答
  • 人間の役割: コードをコピペしてファイルに適用する
  • コンテキスト: 会話履歴 + 貼り付けられたコード

第3世代: エージェント型ツール（2025-現在）

Claude Code、OpenAI Codex CLI、Cursorのエージェントモードなどが登場し、AIが「自律的にコードを書き、テストし、修正する」エージェントとして機能するようになった。これは質的な転換であり、4人の海外ソースが語っているのはこの第3世代の話である。

  • 入力: 高レベルのタスク記述（「認証システムを実装して」）
  • 出力: ファイルの直接編集、テストの実行、デバッグ
  • 人間の役割: 設計判断、レビュー、承認
  • コンテキスト: プロジェクト全体 + ファイルシステム + 外部ツール

A.4 エージェント工学（Agentic Engineering）の学術的背景

「エージェント工学」は2025年から2026年にかけて急速に成熟した分野である。arXivに掲載された研究論文「Agentic Software Engineering: Foundational Pillars and a Research Roadmap」は、この分野の学術的な基盤を示している。

エージェント工学の定義: 「目標を自律的に追求するAIシステムを設計、構築、運用する実践」。これには以下が含まれる:

  • マルチステップタスクの計画（Planning）
  • ツールの使用（Tool Use）
  • エラーからの回復（Error Recovery）
  • リスクが高い場面での人間との協調（Human-in-the-Loop）

エージェントアーキテクチャの主要コンポーネントは、ポリシー/LLMコア、メモリ、世界モデル、プランナー、ツールルーター、クリティックから構成される。これらは4人のソースが語っている内容と直接対応する:

  • ポリシー/LLMコア = Thariqが語るClaude自体の能力設計
  • メモリ = Thariqのファイルシステム論 + Vasilieのcognee
  • プランナー = SysLSの研究と実装の分離 + VishwasのPlan Mode
  • ツールルーター = Thariqのアクション空間設計
  • クリティック = SysLSの3エージェントSycophancy対策

つまり、4人は学術的なエージェントアーキテクチャの各コンポーネントを、実務的な視点から語っているのである。

2.1 「カルピス理論」— 情報希釈の4段階モデル

こはくは情報の希釈過程を「カルピス」に喩えている。原液が末端に届く頃には10分の1に薄まる、と。このメタファーを構造的に分解すると、以下の4段階モデルが見えてくる:

100%原液
→
翻訳
70-80%
→
解説記事
40-50%
→
解説の解説
10-20%

この各段階で具体的に何が失われるかを検証する。

Stage 1 → Stage 2: 翻訳での情報損失

技術翻訳における損失は、単なる言語変換の問題ではない。2026年時点のAI翻訳精度は大幅に向上しているが、以下の問題は依然として残る:

  • 技術用語の多義性: 「context」は文脈・状況・コンテキストウィンドウ・実行コンテキストなど、AIの文脈では複数の意味を持つ。どの訳を選ぶかで理解が変わる
  • 暗喩と文化的参照: Thariqの"Cache Rules Everything Around Me"はWu-Tang Clanの"C.R.E.A.M. (Cash Rules Everything Around Me)"のパロディ。この文化的レイヤーは翻訳で消える
  • ニュアンスの喪失: "Claude seemed to like calling this tool"という表現には、モデルの振る舞いを擬人化して設計判断を語るという重要なニュアンスがある
  • 時間的遅延: 翻訳には物理的な時間がかかる。急速に変化するツールの文脈では、翻訳完了時に情報が陳腐化していることがある

Stage 2 → Stage 3: 解説記事での情報損失

解説者のフィルターを通ることで、以下が失われる:

  • 選択バイアス: 解説者が「面白い」と判断した部分だけが取り上げられる。Thariqの記事でAskUserQuestionToolが3回の失敗を経て完成した経緯は、多くの解説で省略される
  • 文脈の切断: 個々のTipsが独立した断片として扱われ、5本の記事が形成する体系的な設計哲学が見えなくなる
  • 難易度の平準化: 読者層を意識して技術的詳細が省略され、「プロンプトキャッシュを使おう」レベルの結論だけが残る
  • 批判的視点の欠如: 元記事への反論や限界の指摘が省かれ、無条件の推奨に変わる

Stage 3 → Stage 4: 解説の解説での情報損失

最終段階では、情報はほぼ別物になっている:

  • 具体的なコード例や設計判断が消え、抽象的なアドバイスだけが残る
  • 「CLAUDE.mdを書こう」→「AIに指示書を書こう」→「AIをちゃんと使おう」と一般化が進む
  • 原著者の名前すら消え、「海外ではこうしてる」という漠然とした権威付けになる
  • 複数ソースの情報が混ざり、誰が何を言ったか追跡不能になる

2.3 情報エコシステムの比較分析 — 英語圏 vs 日本語圏

英語圏のAI情報エコシステム

英語圏のAI情報エコシステムは、複数の階層で構成されている。このエコシステムの厚みが、末端でも一定の品質を保てる理由である。

階層1: 開発企業の公式発信 — Anthropic、OpenAI、Google DeepMind等の開発企業が、自社のモデルやツールの設計思想、技術的詳細、ベストプラクティスを直接発信する。Anthropicのエンジニアリングブログ、OpenAIのCookbook、GoogleのBlogなどが代表的である。この階層の情報は最も信頼性が高く、Thariqの「Lessons from Building Claude Code」シリーズはまさにこの階層に属する。

階層2: パワーユーザーと独立リサーチャー — SysLS、Addy Osmani、Simon Willison等の実務家が、自身の経験に基づいた知見を発信する。この階層は一次情報の「実践的解釈」を提供し、開発企業の公式発信を補完する。英語圏ではこの階層の厚みが圧倒的であり、数百人規模のパワーユーザーがXやブログで継続的に発信している。

階層3: 教育者とコンテンツクリエイター — VishwasのCodevolution、DeepLearning.AIの講座、各種Udemyコースなどが、体系的な教育コンテンツを提供する。この階層は情報の「構造化」と「普及」を担い、初心者から中級者へのブリッジとなる。

階層4: コミュニティとディスカッション — Discord、Reddit、GitHub Discussions、Xのリプライチェーンなどで、日常的な議論が行われる。ここでは問題解決、アイデアの共有、フィードバックが即座に行われ、エコシステム全体の知識が集合的に蓄積される。

階層5: 学術研究 — arXivの論文、大学の研究チーム、企業の研究部門が、理論的な基盤を提供する。エージェントアーキテクチャの形式化、メモリシステムの最適化、コンテキスト管理の理論的分析などが含まれる。

日本語圏のAI情報エコシステム

日本語圏のエコシステムは、英語圏と比較すると以下の特徴がある:

階層1の薄さ: 日本発のAI開発企業（Preferred Networks、ABEJA、Sakana AI等）は存在するが、Claude CodeやCursorのようなグローバルに影響力のあるAIコーディングツールを開発している日本企業はない。このため、「中の人」からの一次情報が日本語で提供されることが極めて少ない。

階層2の構造的弱さ: 日本語圏のパワーユーザーは増加傾向にあるが、英語圏と比較すると量的に不足している。理由として、日本の技術者は企業所属が多く個人での発信が少ないこと、英語コンテンツを消費できる技術者が多いため日本語での再発信の動機が弱いことが挙げられる。こはく自身はこの階層に位置する数少ない存在である。

階層3の偏り: 日本語の教育コンテンツは、入門レベルに偏る傾向がある。「Claude Codeの始め方」は多数あるが、「Claude Codeの設計思想」を語るコンテンツは少ない。これは市場の需要構造（入門者が多い）と供給側の能力制約（深い知見を持つ発信者が少ない）の両方に起因する。

階層4の活性化: Discord、note、Zenn、Qiitaなどのプラットフォームでコミュニティは活発である。ただし、議論の質は英語圏のXリプライチェーンと比較すると表面的になりがちである。これは参加者の専門性の分布に依存する。

階層5の独立性: 学術研究は英語で行われることが多く、日本語圏のAI情報エコシステムとの接続が弱い。日本の大学のAI研究は世界レベルだが、その知見が日本語圏のプラクティショナーに伝わる経路が限られている。

エコシステム間の情報フロー

英語圏から日本語圏への情報フローには、以下の経路がある:

  • 直接アクセス: 英語を読める技術者が直接一次ソースにアクセスする（こはくの推奨する方法）
  • 翻訳記事: Gigazine、ITmedia等のメディアが英語記事を翻訳・要約する（1-2週間の遅延）
  • 解説記事: 技術ブロガーが英語ソースを基に日本語の解説を書く（2-4週間の遅延）
  • 書籍: 技術書として出版される（6-12ヶ月の遅延）
  • AI翻訳: Claude等で即座に翻訳する（遅延なし、ただし個人利用に限定）

AI翻訳の登場により、「直接アクセス」の障壁が大幅に下がった。これは情報格差を縮小する最大の要因であり、こはくの戦略が以前より実行しやすくなっている理由でもある。

2.4 情報劣化のケーススタディ — プロンプトキャッシュの場合

情報がどのように劣化するかを、Thariqのプロンプトキャッシュ記事を具体例として追跡する:

Stage 0: Thariqの原文（一次情報）

Thariqの原文は以下の情報を含む:

  • Claude Codeのプロンプトレイアウト（4層構造）の技術的詳細
  • キャッシュ無効化の具体的リスク（モデル変更、ツール追加、タイムスタンプ等）
  • 遅延ツールロードの実装詳細（defer_loading: true）
  • Plan Modeでツールセットを入れ替えない設計判断とその理由
  • キャッシュヒット率の監視とSEVレベルでの対応
  • 具体的なコスト数値（$50-100 → $10-19）
  • 「Cache Rules Everything Around Me」の文化的参照

Stage 1: 英語圏の解説記事（二次情報）

典型的な英語解説記事では以下が保持される:

  • 4層構造の説明（保持、ただし簡略化）
  • キャッシュ無効化のリスク（一部保持）
  • コスト数値（保持）

以下が失われる:

  • Plan Modeの設計判断の理由（省略されることが多い）
  • defer_loading: trueの実装詳細（省略）
  • SEVレベルの運用規律（省略）

Stage 2: 日本語翻訳記事（三次情報）

典型的な日本語翻訳記事では以下が保持される:

  • 「プロンプトキャッシュが重要」という結論
  • コスト削減の数値（一部）
  • 静的→動的の原則（簡略化）

以下が失われる:

  • 4層構造の正確な説明
  • キャッシュ無効化の具体的リスク
  • 遅延ツールロードの存在自体
  • Plan Mode設計との接続
  • 「Cache Rules Everything Around Me」のWu-Tang Clanパロディ

Stage 3: 日本語の解説の解説（四次情報）

最終的に残る情報:

  • 「Claude Codeにはキャッシュ機能がある」
  • 「コストが安くなる」
  • 「長時間使うと安い」

完全に失われている情報:

  • MCPサーバー追加がキャッシュを破壊してコストが5倍になるリスク
  • セッション途中のモデル変更が致命的であること
  • 遅延ツールロードという解決策の存在
  • Claude Code Pro $20/月の経済的実現可能性がキャッシュ設計に依存していること
  • 設計判断の背後にある哲学（Unix哲学との接続）

Stage 0からStage 3への情報損失は、単なる「薄まり」ではなく「構造的変質」である。最も実用的な情報（「やってはいけないこと」のリスト）が最も早く失われ、最も一般的な結論（「キャッシュは良い」）だけが残る。

ここが核心

一次情報の最大の価値は「何をすべきか」ではなく「何をしてはいけないか」にある。Gotchas（落とし穴）、Anti-patterns（アンチパターン）、Design trade-offs（設計のトレードオフ）は、情報伝達の過程で最も早く失われる要素である。これこそが、情報の上流にいることの構造的メリットである。

2.3 情報格差の構造的要因

なぜこの格差が生まれるのか。構造的要因は複数ある:

供給側の問題

  • 一次情報を出す人が少ない: 技術的深度のある一次情報を発信するには、実際にツールを深く使い込む必要がある。これは時間と労力の投資であり、日本語圏では「儲からない」ため供給が少ない
  • 英語の壁: 海外ソースを直接読める技術者は多いが、それを日本語で体系的に発信する人は少ない。読む能力と発信する能力は別物
  • インセンティブ構造: 日本のtech系メディアは「バズるコンテンツ」を求め、深い技術記事は収益性が低い。結果として「AIで整えた薄い文章」が量産される

需要側の問題

  • 受動的消費: ブックマークを増やして満足する層が多く、実装に移す層が少ない
  • 英語忌避: 技術者でも英語ドキュメントを避ける傾向がある
  • コミュニティの分断: 英語圏のDiscordやX (Twitter)での議論に参加する日本人が少ない

流通構造の問題

  • 伝言ゲーム構造: 一次情報→翻訳→解説→解説の解説の多段階構造
  • 品質フィルタの不在: 技術的正確性を検証するメカニズムが弱い
  • アルゴリズムによる増幅: SNSのアルゴリズムは「バズる」コンテンツ（≠正確なコンテンツ）を優先する
重要な注意点

情報格差の問題は「日本が悪い」という単純な話ではない。英語圏でも同様の薄まりは起きている。ただし、英語圏の場合は一次情報の供給量が圧倒的に多いため、末端でも一定の質が保たれる。日本語圏は供給量が少ないため、薄まりの影響がより深刻になる。

スキルの定義と本質

Thariqによれば、スキルはClaude Codeの「最も使われている拡張ポイント」の1つであり、柔軟で作りやすく、配布が簡単である。しかし、この柔軟性ゆえに「何がベストか」が分かりにくい。

スキルの本質は、Markdownファイルで書かれた指示セットであり、必要な時だけロードされる。全てのスキルを常時ロードする必要はない。これはコンテキストウィンドウの制約を考慮した設計判断である。

アクション空間（Action Space）とは

エージェントハーネスを構築する際の最も困難な部分の1つは、その「アクション空間」を構築することである。アクション空間とは、モデルが取りうる選択肢の宇宙、すなわちモデルが「何ができて何ができないか」の定義のことである。

Thariqはこれを数学の問題に喩えている: 紙とペンだけなら計算力は限定されるが、コンピュータとコーディング能力があれば可能性が劇的に拡がる。ツールの設計は、エージェントの「能力の上限」を決定する。

AskUserQuestionToolの3回の失敗

この記事の最も価値ある部分は、Thariqが3回の失敗をオープンに語っている点である:

Attempt 1 — ツールパラメータアプローチ

既存のExitPlanToolに質問配列を追加するアプローチ。結果: モデルは計画を生成しつつユーザーの回答の矛盾を解決するという論理的な衝突を処理できなかった。1つのツールに複数の責務を詰め込んだことが失敗の原因。

Attempt 2 — 出力フォーマット変更

質問用のMarkdownフォーマットを再構造化するアプローチ。結果: Claudeは不安定にテキストを追加したり、オプションを省略したり、指定フォーマットから逸脱した。出力形式に「お願い」するだけでは制御が不十分だった。

Attempt 3 — 専用AskUserQuestionTool（成功）

専用の独立したツールとして設計。結果: Claudeはこのツールを「好んで」呼び出すようになった。構造化された出力、確実な複数オプション、そしてモーダル表示によるブロッキングが実現した。

設計原則

この3回の失敗から導かれる原則: 「1ツール = 1責務」。ツールの設計は、ソフトウェア設計の単一責任原則と同じ原理に従う。複数の機能を1つのツールに詰め込むと、モデルの認知負荷が増し、使用パターンが不安定になる。

Progressive Disclosure（段階的情報開示）

全てのコンテキストをシステムプロンプトに詰め込むのではなく、Claude Codeは段階的な情報アクセスを実装している:

  • ネストされたファイル検索によるオンデマンドの情報取得
  • スキル参照による必要時のみの知識ロード
  • 専門サブエージェント（Claude Code Guide等）への委譲

このアプローチは「コンテキスト腐敗（context rot）」を防ぎつつ、エージェントの機敏性を維持する。

Todos → Tasks の進化

初期のTodoリストは5ターンごとにシステムリマインダーが必要だった。しかしClaudeの能力が向上するにつれ、これらのリマインダーは「助け」ではなく「制約」になった。TasksがTodosを置き換え、エージェント間の調整と動的な変更が可能になった。

"As model capabilities increase, the tools that your models once needed might now be constraining them."

— Thariq (@trq212)

これは極めて重要な洞察である。AIツールの設計は、モデルの能力向上に合わせて継続的に見直す必要がある。過去に有用だったガードレールが、将来は足枷になる可能性がある。

Thariq自身が「1日で書いたが数ヶ月の学びの集大成」と述べたこの記事は、Claude Codeの経済的実現可能性を支える最重要アーキテクチャを解説している。

プロンプトキャッシュがなければ、Claude Code Proの$20/月は経済的に成り立たない。これがThariqが「Cache Rules Everything Around Me」と言う理由である。

静的→動的レイアウト原則

最適なキャッシュヒットを実現するための核心原則: 「静的コンテンツを先に、動的コンテンツを最後に」

// Claude Codeのプロンプトレイアウト

Layer 1: 静的システムプロンプト＆ツール定義 → 全ユーザーで共有キャッシュ

Layer 2: プロジェクトコンテキスト (CLAUDE.md) → 同じプロジェクトの全メンバーで共有キャッシュ

Layer 3: セッションコンテキスト → セッションレベルキャッシュ

Layer 4: 会話メッセージ → 動的（キャッシュなし）

このレイヤー構造により、プレフィックスマッチングが最大化される。全ユーザーが同じシステムプロンプトキャッシュを共有し、プロジェクトメンバーがCLAUDE.mdキャッシュを共有し、会話だけがセッション固有となる。

キャッシュを壊す行為（危険リスト）

キャッシュ無効化リスク
  • モデルの変更: セッション途中でモデルを切り替えると、全キャッシュが再構築される
  • ツールの追加/削除: MCPサーバーを追加するとプレフィックスが変わりキャッシュが無効化される
  • システムプロンプトの変更: タイムスタンプをシステムプロンプトに入れると毎回キャッシュが壊れる
  • 非決定的なツール順序: ツールの順序が変わるとキャッシュが効かなくなる

スマートな回避策

  • プロンプト変更ではなくシステムメッセージ: 情報更新（タイムスタンプ、ファイル変更通知等）はプロンプト編集ではなくシステムメッセージで行う
  • Plan Mode設計: 「Plan Mode」に入るとき、ツールセットを入れ替えるのではなく、全ツールを維持したままEnterPlanMode/ExitPlanModeをCallableツールとして提供し、システムメッセージで指示を出す
  • 遅延ツールロード: MCPツールはdefer_loading: trueの軽量スタブとして定義し、選択時のみ完全スキーマをロードする
  • キャッシュ安全な圧縮: 会話を要約（compaction）する際、親セッションと同じシステムプロンプト・コンテキスト・ツールを使用し、キャッシュされたプレフィックスを保持する

運用規律

Thariqのチームはプロダクションアラートでキャッシュヒット率を監視し、低下するとSEV（重大インシデント）を宣言する。わずかな割合の低下でもコストとレイテンシに大きな影響を与えるからだ。

4.4 記事④: Making Playgrounds（プレイグラウンドの活用）

4.5 記事⑤: Your Agent should use a File System（ファイルシステムを使え）

2025年9月23日公開 | Thariqが「死守する丘」と呼ぶ哲学

"This is a hill I will die on"

Thariqが自身の信念を最も強く表明した記事である。「全てのエージェントがファイルシステムを使うべきだ」——これはThariqが「命を懸けてでも主張する」テーゼである。

核心的な洞察

従来のアプローチは「コンテキストウィンドウを拡大して全コードベースを収容する」ことだった。しかし実際のプログラミングは異なる。重要なのは「全てを覚えること」ではなく「必要な情報を見つける方法を知ること」である。

ファイルシステムはこの「知識マネジメント」を優雅に解決する:

  • 無限の容量: コンテキストウィンドウの制約を超えた情報保持
  • セッション間の永続性: 会話が終わっても情報が残る
  • 検索可能性: grepで即座に検索できる
  • 人間可読フォーマット: JSON/Markdownで人間も直接読める
  • 監査証跡: gitで追跡可能、複数エージェントが協調できる

3段階記憶法

Thariqが推奨する実装パターン:

  1. Scratchpad（メモ帳）: 思考中の一時的なメモ。現在のタスクに関する作業メモリ
  2. Plan（計画）: タスクの全体計画と構造。実行の羅針盤
  3. Progress（進捗）: 完了したステップと結果の記録。学習ログ

この3つを分離ファイルで管理することで、エージェントは問題に段階的にアプローチできる。これはコンピュータアーキテクチャのキャッシュ階層（L1/L2/L3）に類似している。Scratchpadは高速アクセスの作業メモリ（L1）、Planは中期的な参照情報（L2）、Progressは長期的な記録（L3/メインメモリ）に対応する。

具体的なファイル実装例

# scratchpad.md — 思考中の一時メモ

## 現在のタスク
認証ミドルウェアのリファクタリング

## 観察
- 既存のmiddleware.tsはEdge Runtimeで動いている
- NextAuth.js v5はEdge Runtimeをネイティブサポート
- 現在のセッション検証はDBアクセスしている（Edge非対応）

## 仮説
- JWTベースに切り替えればEdge Runtimeで完結できるのでは？
- ただしJWTのサイズ制限に注意が必要
# plan.md — タスクの全体計画

## 目標
認証をJWTベースに移行し、Edge Runtimeで完結させる

## ステップ
1. [x] 現在の認証フローを調査
2. [x] NextAuth.js v5のJWT設定を確認
3. [ ] middleware.tsをJWTベースに書き換え
4. [ ] セッション関連のAPIルートを更新
5. [ ] 既存テストを更新
6. [ ] E2Eテストを実行

## 制約
- 既存のセッションの互換性を維持すること
- DBスキーマの変更は最小限にすること
# progress.md — 完了したステップの記録

## Session 1 (2026-03-23 14:00)
- ステップ1, 2を完了
- 発見: NextAuth.js v5ではcallbacks.jwtでカスタムクレームを追加可能
- 落とし穴: Edge Runtimeではcryptoモジュールが制限される
- 次回: middleware.tsの書き換えから開始

## Session 2 (2026-03-23 15:30)
- ステップ3を完了
- 問題: JWTのペイロードが4KBを超えるとCookieに収まらない
- 解決: 必要最小限のクレームのみJWTに含め、詳細はAPIで取得

この3段階記憶法の強力な点は、エージェントが「思考の連続性」を失わないことである。セッションが切り替わっても、progress.mdを読めば前回の状態を復元できる。compactionで会話が要約されても、plan.mdの構造は保持される。これはThariqが「ファイルシステムはエレガントな状態表現」と述べた所以である。

Bash is all you need

Thariqはまた「Bashこそが最初のコードモード」であると主張している。Bashツールは合成可能（composable）で、発見可能（discoverable）であり、既存のソフトウェア（ffmpeg, jq等）をカスタムツールを構築せずに使える。これはファイルシステムの哲学と通じている — Unixの哲学「全てはファイル」を、AIエージェントの世界に持ち込んでいるのだ。

記事の行間に隠された設計判断と、Claude Codeの未来

B.1 「Bash is all you need」— Unix哲学のAIエージェントへの応用

Thariqが繰り返し強調する「Bash is all you need」は、単なるツールの推奨ではない。これはUnix哲学をAIエージェント設計に移植する思想的宣言である。

Unix哲学の核心原則:

  • Do one thing well（一つのことを上手くやれ）: 各プログラムは単一の機能に特化する
  • Everything is a file（全てはファイル）: デバイスもプロセスもネットワークも、ファイルインターフェースで統一的にアクセスできる
  • Compose small programs（小さなプログラムを組み合わせろ）: パイプ（|）で複数のプログラムを連結し、複雑な処理を実現する
  • Text is the universal interface（テキストが普遍的インターフェース）: プログラム間のデータ交換はテキストストリームで行う

これらの原則はAIエージェントに直接適用可能である:

Unix原則 エージェント設計への適用 Thariqの実装例
Do one thing well 1ツール = 1責務 AskUserQuestionToolの独立設計
Everything is a file ファイルシステムがメモリ scratchpad/plan/progressの3段階
Compose small programs Skillsの組み合わせ 9カテゴリのスキルを必要に応じてロード
Text is the universal interface Markdownが共通フォーマット SKILL.md, CLAUDE.md, AGENTS.md

Bashツールが「最初のコードモード」として選ばれた理由も、この哲学に基づく。Bashは合成可能（composable）であり — grep、sed、awk、jq等の既存ツールをパイプで組み合わせられる。発見可能（discoverable）であり — manコマンドや--helpフラグで使い方を調べられる。そして既存のソフトウェアエコシステムを活用できる — ffmpeg、ImageMagick、curl等、数十年の歴史を持つツールをカスタムツールを構築せずに使える。

深い設計判断

カスタムツールを多数作るアプローチ（MCPサーバーの増殖）は、Unix哲学に反する。少数の汎用的なツール（Bash、Read、Write、Grep、Glob）を組み合わせる方が、コンテキストウィンドウの消費が少なく、キャッシュ効率も高い。Thariqが遅延ツールロード（defer_loading: true）を導入した理由も、MCPツールの増殖がキャッシュを破壊するからである。

Thariqが「最も好きなClaude Codeの使い方」として公開したワークフローは、4人の思想が実践レベルで収束する最も明確な例である:

# Thariqのspec-basedワークフロー

    例: "JWTベースの認証システムが必要"

    → 結果: 詳細なスペック文書が生成される

Step 3: 新しいセッションを作ってスペックを実行する
    → クリーンなコンテキストでスペックに基づいて実装

このワークフローが優れている理由:

  • キャッシュ効率: 新しいセッションはシステムプロンプトとCLAUDE.mdのキャッシュを再利用できる
  • Task Contract的機能: スペック文書が事実上のTask Contractとして機能する

B.3 キャッシュ設計の経済学 — 知られざるコスト構造

Thariqのプロンプトキャッシュ記事は、多くの解説で「キャッシュを使おう」レベルに要約される。しかし、本質的に重要なのはキャッシュがClaude Codeのビジネスモデルそのものを成立させている構造的な役割である。

コスト構造の詳細分析

Claude Opus 4.6の入力トークン価格を仮に$15/MTk（100万トークンあたり$15）とすると:

シナリオ 100ターンの入力トークン合計 キャッシュなしコスト キャッシュありコスト 節約率
短いセッション（10K/turn） ~500K（累積） $7.50 $1.50 80%
中程度のセッション（50K/turn） ~2.5M（累積） $37.50 $7.50 80%
長いセッション（100K/turn + compaction） ~5M（累積） $75.00 $15.00 80%

$20/月のProプランでこの品質を提供するには、キャッシュヒット率が80%以上でなければ経済的に成り立たない。だからこそThariqのチームはキャッシュヒット率の低下をSEV（重大インシデント）として扱うのである。

ユーザーが意図せずキャッシュを破壊するパターン

  1. セッション途中でのモデル変更: 「Sonnetで試してうまくいかないからOpusに切り替え」→ 全キャッシュ再構築、コスト5倍
  2. MCPサーバーの動的追加: 「このMCPサーバーも入れてみよう」→ ツール定義が変わりプレフィックス不一致
  3. CLAUDE.mdの頻繁な編集: セッション中にCLAUDE.mdを何度も編集 → プロジェクトレベルキャッシュが毎回無効化
  4. タイムスタンプ付きプロンプト: 「現在時刻は○○です」をシステムプロンプトに含める → 毎回キャッシュミス

これらの問題は、Thariqの記事を読まない限り気づけない。これこそが「一次情報の価値」の具体例である。解説記事では「キャッシュを活用しましょう」とは言うが、「MCPサーバーを追加するとキャッシュが壊れてコストが5倍になる」とは言わない。

B.4 Playgroundの思想的意義 — テキスト対話の限界を超える

Playgroundプラグインは一見するとニッチなツールだが、Thariqの思想体系の中では重要な位置を占める。これは「テキストプロンプティングの限界」への回答である。

エージェントとの対話がテキストだけに限定されると、以下の問題が生じる:

  • 空間的情報の伝達困難: 「このボタンをもう少し右に」はテキストで伝えにくい
  • 反復的調整の非効率: 色やサイズの微調整は「#3498db → #2980b9に変更して」を何度も繰り返す必要がある
  • 全体像の把握困難: アーキテクチャの全体像をテキストで議論するのは困難
  • 暗黙的な知識の伝達: 「この感じが欲しい」はテキストでは表現しにくい

Playgroundはこれらの問題を、インタラクティブなHTMLインターフェースで解決する。スライダーやカラーピッカーで直感的に調整し、その結果をプロンプトとしてClaude Codeにフィードバックする。これは人間とAIの対話モダリティの拡張であり、将来的にはAR/VR、音声、ジェスチャーなど、さらに多様な対話モダリティへの道を開く可能性がある。

5.1 原則①: Context is Everything（文脈が全て）

Context Bloat Syndrome（コンテキスト肥大症候群）

SysLSの最初にして最も重要な原則は、コンテキスト管理に関するものだ。彼は「Context Bloat Syndrome」という概念を提唱し、エージェントに不必要な情報を詰め込みすぎる問題を指摘する。

"You only want to give the agent exactly enough information to complete the task, no more, no less."

— SysLS (@systematicls)

具体的に問題となるのが、MCPサーバーの入れすぎである。SysLSは「MCPサーバーを10個も入れているやつ」を明確に批判する。なぜなら:

  • 各MCPツールの定義がコンテキストウィンドウを消費する
  • ツールの選択肢が増えるほど、モデルの判断が分散する
  • Thariqの記事と照合すると、各MCPツールがプロンプトキャッシュを無効化するリスクがある
  • 不必要なツールの存在は、モデルが不要なツールを呼び出す確率を高める

これはAnthropicのコンテキストエンジニアリングガイドで確認された「context rot」現象と一致する — コンテキストウィンドウ内のトークン数が増加するにつれ、モデルの情報リコール精度が低下する。

最小コンテキスト原則の実践

SysLSが推奨する具体的な実践:

  • MCPサーバーは2-3個まで: 本当に必要なものだけ
  • CLAUDE.mdは簡潔に: 長大なルールリストではなく、本質的な原則のみ
  • プラグインの定期監査: 使っていないプラグインは即座に削除
  • タスクごとのコンテキスト設計: 汎用的なセットアップではなく、タスクに最適化されたコンテキスト

5.2 原則②: 研究と実装の分離

曖昧な指示がバグの温床

SysLSは、エージェントへの指示を「研究フェーズ」と「実装フェーズ」に明確に分離することを主張する。

悪い指示（曖昧）

  • JWT? Session? OAuth?
  • パスワードハッシュは何を使う?
  • トークンの有効期限は?
  • セッション管理はどうする?

良い指示（具体的）

「JWT認証、bcrypt-12ラウンド、トークン有効期限7日で実装して」

→ 明確なスペック:

  • 認証方式: JWT
  • ハッシュ: bcrypt 12ラウンド
  • 有効期限: 7日
  • 曖昧さゼロ

= 高品質な出力

2段階ワークフロー

SysLSが推奨するワークフロー:

  1. 研究フェーズ: エージェントに徹底的な調査をさせ、具体的な実装方針を決定する。ここではPlan Modeを活用し、ファイル読み取りと検索のみを許可する
  2. 実装フェーズ: 「brand-new context（完全に新しいコンテキスト）」を持つ別のセッション/エージェントに、研究フェーズの成果（＝具体的なスペック）を渡して実装を委譲する

5.3 原則③: Sycophancy対策（おべっか問題）

AIの同調性を逆利用する

AIモデルは本質的にsycophantic（おべっか的）である — ユーザーの指示に従おうとしすぎる傾向がある。「バグを探せ」と言えば、存在しないバグも報告してくる。SysLSはこの特性を問題として認識しつつ、逆利用する戦略を提案する:

3エージェント構成

エージェント 役割 スコアリング 行動パターン
Bug Hunter
(バグ探しエージェント)		 可能な限り多くのバグを発見 発見数に応じてスコア (+1, +5, +10) Sycophancyを利用して過剰検出（上位集合を取得）
Adversarial Agent
(反論エージェント)		 Bug Hunterの発見に反論 正当な反論でスコア加算、誤った反論でペナルティ 偽陽性を排除して下位集合を抽出
Judge Agent
(審判エージェント)		 両者の議論を総合判断 最終判定 中立的立場で客観的に評価

この構成は、法廷の「弁護士 vs 検察 vs 裁判官」モデルに類似している。1つのエージェントに「正確に判断しろ」と言うのではなく、対立する立場のエージェントを配置して構造的に正確性を担保する。

補足: 中立的プロンプティング

SysLSは追加の対策として「中立的プロンプト」も推奨する。「指示通りに実行せよ」（＝従順を誘発）ではなく「客観的に報告せよ」（＝中立性を誘発）という指示の方が、sycophancyの影響を受けにくい。

5.4 原則④: CLAUDE.md設計 — ファイルからディレクトリへ

従来のアプローチの限界

多くのユーザーがCLAUDE.mdを1つの巨大なファイルとして書いている。全てのルール、スタイルガイド、ワークフロー、例外処理を1ファイルに詰め込む。SysLSはこれを「もう古い」と断言する。

ディレクトリ設計のアプローチ

SysLSの提案するCLAUDE.mdは、ルートファイルをディスパッチャーとして使い、IF-ELSEロジックで必要なファイルを動的に参照する:

# CLAUDE.md（ルートファイル = ディスパッチャー）

## コーディングタスクの場合
→ coding-rules.md を読み込め

## テストの場合
→ testing-standards.md を読み込め

## デプロイの場合
→ deployment-checklist.md を読み込め

## レビューの場合
→ review-process.md を読み込め

核心原則: Compression, Context, Assumptions

CLAUDE.md設計の3つの柱:

  • Compression（圧縮）: 最小限の情報で最大の効果を出す。冗長な説明を排除
  • Context（文脈）: タスクに必要な文脈だけを動的にロード
  • Assumptions（仮定）: エージェントが勝手に仮定を埋めるのを防ぐ

「再読指令」の重要性

SysLSの最重要ルール

"Re-read your task plan and re-read the files related to the current task"
CLAUDE.md読み込み直後にこの指示を実行させる。エージェントが「自動補填」（自分で仮定を埋めてしまうこと）に陥るのを防ぎ、品質低下を抑止する。仮定を埋める代わりにファイルを読ませる。

5.5 原則⑤: Task Contract（タスク契約）

「いい感じにして」が永遠に終わらない問題

エージェントに「いい感じにして」と指示すると、エージェントは永遠に改善を続ける。なぜなら「完了」の定義がないからだ。SysLSはこの問題を「Task Contract（タスク契約）」で解決する。

{Task Name}_CONTRACT.mdの構造

# auth-system_CONTRACT.md

## 完了条件
1. 全ユニットテストが通過する
2. 全E2Eテストが通過する
3. ログインフローのスクリーンショットが期待通り
4. セキュリティスキャンで重大な脆弱性がゼロ

## 検証方法
- npm test → 全テストパス
- playwright test → スクリーンショット比較
- npm audit → 脆弱性ゼロ

## 禁止事項
- 既存APIの変更
- 新しい依存パッケージの追加

「1契約 = 1セッション」原則

SysLSは複数契約の混在を避けることを強く推奨する。理由は「文脈汚染」——異なるタスクのコンテキストが混ざると、エージェントの判断精度が低下するからだ。

さらに「Stop-hook」を設定して、エージェントが契約完了前に自動的に終了するのを防ぐ。これはClaude Codeのhooksシステムを活用した実装である。

5.6 SysLS思想の統合 — 最小主義のエンジニアリング

SysLSの5原則を貫くメタ原則は「最小主義（Minimalism）」である:

  • コンテキストは最小限（Context is Everything）
  • タスクは明確に分離（研究と実装の分離）
  • 判断は構造で担保（Sycophancy対策）
  • 設定は動的に必要なものだけ（CLAUDE.md設計）
  • 完了は明確に定義（Task Contract）

「最新ツールを追いかけるより、基本的なCLIと原則的理解に基づく最小構成こそが、本番環境での最高パフォーマンスを実現する。」

— SysLS (@systematicls) の思想を要約

SysLSの「Context is Everything」原則を日常的に実践するためのチェックリスト:

セッション中

セッション終了時

  • 学んだ失敗パターン（Gotchas）をスキルに追加したか
  • 重要な判断をファイルに永続化したか（Thariqのファイルシステム論）
  • 次のセッションのためのメモを残したか

6.2 自己改善ループ — 4ステップモデル

Vasilieが提案する解決策は、スキルに「自己改善ループ」を組み込むことである:

Step 1: 観察（Observe）

スキルが実行されるたびに、その結果を自動的に記録する。成功/失敗のバイナリだけでなく、実行時間、使用したツール、生成されたコードの品質メトリクスなどを構造化されたログとして保存する。

Step 2: 検査（Inspect）

蓄積された実行ログから失敗パターンを自動分析する。「この種のタスクで頻繁に失敗する」「この指示が曖昧なためにモデルが異なる解釈をする」といったパターンを検出する。

Step 3: 修正（Modify）

検出された問題に基づいてスキルの指示を改善する。Gotchasセクションに新しいエントリを追加したり、曖昧な指示を明確化したり、古いAPI呼び出しを更新したりする。

Step 4: 評価（Evaluate）

改善されたスキルが実際に以前の問題を解決できるか検証する。リグレッション（退行）がないことを確認し、改善が持続的であることを保証する。

6.5 自己改善ループの技術的実装 — 詳細解説

Vasilieの4ステップモデルを技術的に掘り下げ、実際にどう実装するかを解説する。

Step 1: 観察（Observe）の実装

スキル実行の結果を構造化ログとして記録するには、以下の情報を各実行ごとに保存する:

# execution_log.jsonl — 追記専用ログ

{
  "timestamp": "2026-03-23T14:30:00Z",
  "skill": "code-review",
  "task": "認証ミドルウェアのレビュー",
  "result": "partial_success",
  "issues": [
    "Edge Runtimeの制約を見落とした",
    "JWTサイズの問題を指摘できなかった"
  ],
  "tokens_used": 15420,
  "duration_seconds": 180

このログは、Thariqのファイルシステム哲学に基づいてファイルとして永続化する。JSON Lines形式にすることで、grepやjqで即座に検索・分析できる。

Step 2: 検査（Inspect）の実装

蓄積されたログからパターンを検出する。最も単純な実装はgrepベース:

# 失敗パターンの分析
$ grep "partial_success\|failure" execution_log.jsonl | \
  jq '.issues[]' | sort | uniq -c | sort -rn

# 出力例:
  5 "Edge Runtimeの制約を見落とした"
  3 "型定義の不整合を見逃した"
  2 "テストカバレッジの確認を忘れた"

より高度な実装では、cogneeのナレッジグラフを使って、失敗パターン間の関係性（「Edge Runtimeの制約を見落とす」と「middleware.tsの変更」が頻繁に共起する）を自動検出できる。

Step 3: 修正（Modify）の実装

検出されたパターンに基づいて、スキルのGotchasセクションを自動更新する。例えば、上記の分析から「Edge Runtimeの制約を見落とした」が頻出パターンであれば:

# 自動追加されるGotchasエントリ

## Gotchas

### Edge Runtime制約（自動検出: 5回の失敗から）
middleware.tsやEdge Runtimeで動作するコードを変更する場合:
- Node.js固有のAPIは使用不可（fs, path, crypto等の一部）
- データベースへの直接アクセス不可
- グローバル変数の永続化不可
→ 変更前に必ず対象ファイルのランタイム環境を確認すること

Step 4: 評価（Evaluate）の実装

改善されたスキルが実際に問題を解決できるかを検証する。最もシンプルな方法は、過去に失敗したタスクを改善後のスキルで再実行し、結果を比較すること。これは本質的にA/Bテストであり、ソフトウェアテストのリグレッションテストに相当する。

実装の簡易版

上記の4ステップを全て自動化する必要はない。最もインパクトが大きいのはStep 1（観察）とStep 3（修正）である。失敗を記録する習慣と、記録に基づいてGotchasを更新する習慣。この2つだけでも、スキルの品質は着実に向上する。自動化は後から追加すればよい。Thariqの「do the simplest thing that works」原則がここでも適用される。

7.1 Tip群①: Subagent活用 — コンテキストを汚さない調査委譲

なぜSubagentが重要か

メインのコンテキストウィンドウは有限リソースである。調査タスク（ファイル検索、API仕様の確認、テストの実行等）をメインエージェントが直接行うと、調査結果がコンテキストを圧迫し、本来のタスクへの集中が損なわれる。

Subagentはこの問題を解決する。調査は別のコンテキストウィンドウで実行され、メインエージェントには凝縮された結果だけが返される。数千トークンの調査結果が、1,000-2,000トークンの要約に圧縮される。

効果的なSubagent設計パターン

  • Explore型: コードベースの検索や構造把握に特化。「このパターンはどこで使われている？」
  • Plan型: 実装計画の立案に特化。アーキテクチャのトレードオフを分析
  • Research型: 外部情報の調査に特化。API仕様やライブラリの調査
  • Verify型: テスト実行と検証に特化。結果のみを報告

VoltAgentプロジェクトは100以上の専門化されたClaude Codeサブエージェントを収集しており、これはSubagent活用の幅広さを示している。

7.2 Tip群②: --worktree — 並列ブランチ開発

Git Worktreeの仕組み

Git worktreeは、同じリポジトリ履歴とリモート接続を共有しながら、独立したファイルとブランチを持つ別の作業ディレクトリを作成する仕組みである。

# Worktreeの基本使用
claude --worktree # 独立したworktreeを作成してClaudeを起動
claude -w # 短縮形

並列セッションの威力

Worktreeを使うことで、3〜5セッションの同時実行が可能になる:

  • Worktree A: フロントエンドのUI改修
  • Worktree B: バックエンドのAPI追加
  • Worktree C: テストの拡充
  • Worktree D: ドキュメント更新
  • Worktree E: バグフィックス

各ワークツリーは独立しているため、互いに干渉しない。incident.ioの事例では、「2時間かかると見積もられたJavaScriptエディタの改修が、並列ワークツリーで10分で完了した」と報告されている。

Subagentとの連携

サブエージェントもworktree分離で実行できる。isolation: worktreeをエージェントの設定に追加するだけで、各サブエージェントが独自のworktreeで作業し、完了後に自動クリーンアップされる。

7.3 Tip群③: Hooks — 自動化の要

Hooksの仕組み

Claude Codeのhooksは、特定のライフサイクルイベントに応じてシェルコマンドを自動実行する仕組みである。主要なイベント:

イベント タイミング 用途
PreToolUse ツール呼び出しの前 危険なコマンドのブロック、バリデーション
PostToolUse ツール呼び出しの後 自動フォーマット、ログ記録、通知
Notification Claude Codeが通知を送る時 Slack通知、メール送信
PostCompact compaction（圧縮）後 重要情報の再注入

実践例: 危険コマンドブロック

// settings.json の hooks設定例
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "command": "check-dangerous-command.sh"
      // exit code 2 → ブロック
    }]
  }
}

実践例: 自動フォーマット

// PostToolUseで自動prettierフォーマット
{
  "PostToolUse": [{
    "matcher": "Edit",
    "command": "prettier --write $TOOL_INPUT_FILE"
  }]
}

7.4 Tip群④: Plan Mode — 設計と実装の分離

Shift+Tabの2段階遷移

Plan ModeはShift+Tabを2回押すことでアクティブになる。このモードでは、Claudeはread-only操作に制限される:

  • ファイルの読み取り
  • コードベースの検索
  • ユーザーへの質問

以下は禁止される:

  • ファイルの書き込み
  • コードの編集
  • シェルコマンドの実行

Thariqの設計意図との接続

Plan Modeの設計には、Thariqのプロンプトキャッシュ戦略が反映されている。Plan Modeに入る際にツールセットを入れ替えるとキャッシュが壊れるため、全ツールを維持したままEnterPlanMode/ExitPlanModeをCallableツールとして提供する設計が採用されている。

Thariqの推奨ワークフロー

Thariq自身が公開した最も好きなワークフロー:

  1. 最小限のスペックまたはプロンプトから始める
  2. ClaudeにAskUserQuestionToolを使ってインタビューさせる
  3. 新しいセッションを作ってスペックを実行する

これはSysLSの「研究と実装の分離」原則と完全に一致する。

7.5 Tip群⑤: Compaction対策 — 長時間セッションの生命線

Compactionとは

Claude Codeの長時間セッションでは、コンテキストウィンドウが限界に近づくと自動的に「compaction（圧縮）」が発生する。会話の初期部分が要約され、トークンが解放される。

問題は、この圧縮過程で重要な情報が失われることがある点だ。プロジェクトのルール、進行中のタスクの詳細、カスタム設定などが圧縮のノイズに埋もれる。

Post-Compaction Hookによる情報再注入

Vishwasが推奨する対策は、PostToolUseフックでcompactマッチャーを使い、圧縮後に重要情報をシステムメッセージとして自動再注入することである:

// Post-Compaction Hook
{
  "PostToolUse": [{
    "matcher": "compact",
    "command": "cat context-essentials.md"
    // stdoutがシステムメッセージとして注入される
  }]
}

context-essentials.mdの設計

再注入する情報は10-50行に厳選すべき。一種の「Before You Ship チェックリスト」として:

  • プロジェクト強制ルール
  • 認証パターン
  • データベースアクセスルール
  • 現在進行中のタスクの状態
  • 絶対に忘れてはいけない制約

2026年3月時点の最新: 1Mコンテキストウィンドウ

Opus 4.6およびSonnet 4.6で1Mトークンのコンテキストウィンドウが一般利用可能になっている。これによりcompactionの頻度は大幅に減少したが、非常に長いセッション（数百ターン）では依然として必要な対策である。

第8章: コンテキストエンジニアリング — 新パラダイム

プロンプトエンジニアリングの次に来るもの

8.1 定義: コンテキストエンジニアリングとは

Anthropicの公式ドキュメントによる定義:

"Context engineering is the strategy of curating and maintaining the optimal set of tokens (information) available during LLM inference."
「コンテキストエンジニアリングとは、LLM推論中に利用可能なトークン（情報）の最適セットをキュレーションおよび維持する戦略である。」

— Anthropic, "Effective Context Engineering for AI Agents"

これはプロンプトエンジニアリングの自然な進化であり、単に「正しい言葉を見つける」ことから、「どの文脈構成が望ましい振る舞いを生み出すか」という包括的な問いへのシフトである。

8.2 パラダイムシフトの背景

プロンプトエンジニアリングの限界

プロンプトエンジニアリングは、実験段階では十分に機能した。しかし、組織がパイロットから本番運用に移行する際に、精度、記憶、ガバナンスの面で単独では不十分であることが明らかになった。

Gartnerは2026年にコンテキストエンジニアリングを企業AI戦略の重要要素として位置付けている。

なぜ今、このシフトが起きているのか

  • エージェントの台頭: 静的なプロンプトではなく、動的で進化するタスク状態を扱う必要がある
  • 長時間セッション: 数百ターンにわたるセッションでは、コンテキストの管理が経済性と品質の両方を左右する
  • マルチツール統合: MCP、ファイルシステム、外部API等、多数の情報ソースを調整する必要がある
  • 品質要件の厳格化: 「面白い回答」から「正確で一貫した回答」へ

8.3 Context Rot — コンテキストの腐敗

Anthropicの研究チームが確認した重要な現象が「context rot（コンテキスト腐敗）」である:

Context Rotの原理

コンテキストウィンドウ内のトークン数が増加するにつれ、モデルの情報リコール精度が低下する。これはTransformerアーキテクチャの根本的な制約に由来する — 各トークンが全コンテキストの他の全トークンに対応する必要があり、n個のトークンに対してn²個のペアワイズ関係が生じる。

つまり、LLMは人間と同様に「注意予算（attention budget）」を持つ有限リソースとして機能する。コンテキストに詰め込むほど、個々の情報への注意は薄まる。これが「必要最小限のコンテキスト」を維持すべき科学的根拠である。

8.4 コンテキストエンジニアリングの実践原則

原則1: システムプロンプト設計 — 適切な「高度」を見つける

Anthropicは「altitude（高度）」という概念を用いる。過度に複雑で脆弱なロジック（低高度）と、曖昧すぎる指示（高高度）の間で、適切なバランスを見つけることが重要である:

  • XMLタグやMarkdownヘッダーで明確にセクション分けする
  • 必要最小限の情報で期待される振る舞いを完全に概説する
  • エッジケースの長いリストより、多様で標準的な例を厳選する（"Examples are the 'pictures' worth a thousand words"）

原則2: ツール設計 — エージェントと世界の「契約」

ツールは「エージェントと情報・行動空間の間の契約」を定義する。設計原則:

  • 機能の重複最小化: 似たツールが複数あると、モデルが選択に迷う
  • 自己完結性: 各ツールが独立して機能する
  • 使用意図の明確性: いつどのツールを使うべきかが曖昧だと、モデルの判断が不安定になる

原則3: Just-in-Time情報取得

全データを事前にロードするのではなく、軽量な識別子（ファイルパス、クエリ、Webリンク）だけを維持し、ランタイム時にツールを使って動的にデータをロードする。Claude Codeはこのパターンを採用しており、bash コマンド（head, tail）でファイルの必要部分のみを読み取る。

原則4: 構造化ノートテイキング

エージェントがコンテキストウィンドウ外のメモリに定期的にメモを保存し、後で取得する方式。これはThariqの「ファイルシステムを使え」哲学の具体的実装である。Claude playing Pokémonの例では、数千ゲームステップにわたって正確なメモリ保持と戦略的なメモが維持された。

原則5: サブエージェント・アーキテクチャ

単一エージェントではなく、専門化された副エージェントが焦点を絞った個別タスクを処理する。各副エージェントは数千トークンを消費しても、1,000-2,000トークンの凝縮要約のみ返却する。これは「コンテキスト圧縮」の最も効果的な形態である。

8.5 コンテキストエンジニアリングの実装パターン集

Anthropicのガイドと4人の思想から、コンテキストエンジニアリングの具体的な実装パターンを整理する。

パターン1: Layered Context Architecture（階層化コンテキスト）

Thariqのプロンプトキャッシュ記事で示された4層構造を一般化したパターン。コンテキストを変更頻度に基づいて階層化する:

層 変更頻度 内容例 キャッシュ戦略
Static Layer ほぼ不変 システムプロンプト、ツール定義 グローバルキャッシュ（全ユーザー共有）
Project Layer 日〜週単位 CLAUDE.md、プロジェクト設定 プロジェクトキャッシュ（チーム共有）
Session Layer セッション内で進化 タスク計画、読み込んだファイル セッションキャッシュ
Dynamic Layer ターンごと ユーザーの指示、ツール結果 キャッシュなし

このパターンの鍵は、各層の境界を明確にし、上位層の変更が下位層に影響を与えないようにすることである。例えば、CLAUDE.mdの小さな修正がシステムプロンプトのキャッシュを無効化しないよう、層間の独立性を維持する設計が必要。

パターン2: Context Budget Management（コンテキスト予算管理）

SysLSの「最小コンテキスト」原則を定量化するパターン。利用可能なコンテキストウィンドウに対して、各要素に「予算」を割り当てる:

要素 推奨予算配分 1Mトークンの場合
システムプロンプト + ツール定義 5-10% 50K-100Kトークン
CLAUDE.md + プロジェクトコンテキスト 5-10% 50K-100Kトークン
スキル定義（ロード済み） 5% 50Kトークン
会話履歴 30-40% 300K-400Kトークン
ツール結果（ファイル読み取り等） 20-30% 200K-300Kトークン
出力バッファ 10-15% 100K-150Kトークン

このパターンにより、「コンテキストが足りない」問題と「コンテキストが多すぎる」問題の両方を防げる。予算を超えそうな場合は、compactionを手動でトリガーするか、Subagentに委譲する。

パターン3: Progressive Context Loading（段階的コンテキストロード）

Thariqの「Progressive Disclosure」を体系化したパターン。コンテキストをlazy loadingの原則で段階的にロードする:

  1. Level 0 (Always Loaded): プロジェクト概要、基本ルール、禁止事項（CLAUDE.mdルートファイル）
  2. Level 1 (Task-Triggered): タスク種別に応じたルールファイル（coding-rules.md等）— CLAUDE.mdの条件分岐でロード
  3. Level 2 (On-Demand): 特定のファイルやAPIドキュメント — エージェントがReadツールで自主的にロード
  4. Level 3 (Delegated): 大量の調査結果 — Subagentに委譲し、要約のみメインコンテキストに返す

各レベルでのロード判断:

  • Level 0: 常時ロード（コスト低い、必須情報）
  • Level 1: タスク開始時に自動判断（CLAUDE.mdの条件分岐）
  • Level 2: エージェントが必要性を判断（Progressive Disclosureの本質）
  • Level 3: 人間またはエージェントが「これは大量の調査が必要」と判断した場合

パターン4: Context Checkpoint & Recovery（コンテキストのチェックポイントと回復）

VishwasのPost-Compaction Hookを拡張したパターン。重要な情報をコンテキストウィンドウの外部に定期的にチェックポイントとして保存し、compaction後に回復する:

# context-checkpoint.sh — 定期的に呼ばれるスクリプト

#!/bin/bash

# 現在のタスク状態を保存
cat <<EOF > .claude/checkpoint/current-state.md
## 現在のタスク
$(cat .claude/tasks/current.md 2>/dev/null || echo "タスク未設定")

## 重要な制約
- APIの破壊的変更禁止
- テストカバレッジ80%以上維持
- Edge Runtimeの制約に注意

## 最近の判断
$(tail -20 .claude/checkpoint/decisions.log 2>/dev/null)
EOF

このスクリプトをPost-Compaction Hookとして設定すると、compaction後に自動的に重要な状態情報が再注入される。

パターン5: Multi-Agent Context Isolation（マルチエージェントのコンテキスト分離）

SysLSの3エージェント構成やVishwasのSubagent活用を支えるパターン。各エージェントのコンテキストを明確に分離し、必要最小限の情報だけを共有する:

  • Main Agent: タスクの全体像、計画、判断の権限を持つ。個々の調査結果は保持しない
  • Explore Agent: コードベースの調査を担当。調査結果の全文はMain Agentに返さず、1,000-2,000トークンの要約のみ返す
  • Review Agent: コードレビューを担当。Main Agentとは独立したコンテキストで、先入観なくレビューする

コンテキスト分離の利点は、「context rot」の影響を各エージェント内に閉じ込められることである。Explore Agentが大量のファイルを読み込んでもそのコンテキスト腐敗はExplore Agentに限定され、Main Agentのコンテキストは清潔に保たれる。

8.6 コンテキストエンジニアリングの数学的基盤

context rotの原理をより深く理解するために、Transformerアーキテクチャの数学的背景を簡潔に解説する。

Self-Attentionの計算量

Transformerのself-attentionメカニズムでは、各トークンが他の全トークンとの関連度を計算する。n個のトークンに対して、計算量はO(n²)である。つまり、コンテキストが2倍になると、各トークンへの「注意の配分」は理論的に半分になる（実際にはattention headの構造により若干緩和される）。

これが「注意予算（attention budget）」の科学的根拠である。100Kトークンのコンテキストでは各トークンへの平均的な注意は、50Kトークンのコンテキストの約半分になる。つまり、不必要なトークンをコンテキストに追加するコストは、そのトークン自体のコストだけでなく、他の全トークンへの注意を薄めるコストでもある。

Lost-in-the-Middle現象

研究により、LLMはコンテキストの先頭と末尾の情報を優先的に参照し、中間部分の情報を見落とす「Lost-in-the-Middle」現象が確認されている。これはrecency biasとprimacy biasの組み合わせである。

この現象への対策:

  • 重要な情報はコンテキストの先頭に: システムプロンプト、CLAUDE.mdの最重要ルール
  • または末尾に: 直近のユーザー指示、最新のタスク計画
  • 中間にはツール結果を: ファイル読み取り結果等、参照が必要だが最重要ではない情報
  • 長いコンテキストは要約を冒頭に置く: 大量の調査結果の前にkey findingsの要約を配置

Thariqの「静的コンテンツを先に、動的コンテンツを最後に」原則は、キャッシュ効率だけでなく、この認知バイアスへの対策でもある。静的で重要なルール（先頭）と最新のユーザー指示（末尾）が優先的に参照され、中間のツール結果は必要に応じて参照される。

コンテキストウィンドウの経済学

1Mトークンのコンテキストウィンドウが利用可能な2026年3月時点でも、「全てをコンテキストに入れる」アプローチは推奨されない。理由:

  • Context rotによる精度低下: コンテキストが大きいほど、特定の情報への注意が薄まる
  • Lost-in-the-Middle: 中間部分の情報が事実上無視される
  • コスト: 入力トークンへの課金（APIの場合）またはレート制限（Proプランの場合）
  • レイテンシ: トークン数に比例して処理時間が増加

つまり、1Mトークンが利用可能であっても、SysLSの「最小コンテキスト」原則は依然として有効である。1Mトークンは「全てを入れる」ためではなく、「長時間セッションでもcompactionなしに作業できる」ために活用すべきである。

Anthropicの結論

"Find the smallest set of high-signal tokens that maximize the likelihood of your desired outcome."
「望む結果の可能性を最大化する、最小限の高シグナルトークンセットを見つけよ。」
これはシステムプロンプト、ツール、例、メッセージ履歴の全てに適用される普遍的原則である。

9.2 エージェント工学の7原則

4人の思想を統合し、エージェント工学の7つの原則として体系化する:

原則1: 最小コンテキスト

タスク完了に必要な最小限の情報だけをコンテキストに含める。「足りないかも」より「多すぎるかも」を警戒する。Context rotは不可逆。

原則2: 責務の分離

研究と実装、計画と実行、批判と擁護を分離する。1つのエージェント/ツールに複数の責務を持たせない。

原則3: 失敗からの学習

成功パターンより失敗パターン（Gotchas）に高い情報価値がある。失敗を記録し、分析し、スキルに反映する。

原則4: 構造的品質保証

個人の注意力に依存せず、対立構造（Bug Hunter vs Adversarial vs Judge）で品質を担保する。

原則5: 永続的記憶

ファイルシステムとナレッジグラフで記憶をコンテキストウィンドウの外に持ち出す。「全てを覚える」より「見つけ方を知る」。

原則6: 経済的設計

キャッシュヒット率を最大化する設計。静的→動的のレイアウト原則。キャッシュを壊す行為を認識し回避する。

原則7: 継続的進化

スキルは書いて終わりではない。観察→検査→修正→評価の自己改善ループを回す。モデル能力の向上に合わせてツールも進化させる。

9.5 プロジェクト規模別の適用ガイド

小さな個人プロジェクトでは、オーバーエンジニアリングを避けることが最も重要。以下だけを適用する:

チームプロジェクト（2-5人、10-50ファイル）

  • 中優先: Worktree並列開発、3エージェント構成（レビュー時）
  • 低優先: cognee導入、自動化された自己改善ループ

大規模プロジェクト（5人以上、100ファイル以上）

大規模プロジェクトでは、4人の教えの全てが必要になり、さらにスケーリングの課題が追加される:

  • 追加で必要: MCPサーバーの戦略的選定（defer_loading活用）、キャッシュヒット率の監視、チーム間のスキル共有メカニズム
  • 検討すべき: cogneeの導入（大量ドキュメントの管理）、自動化された自己改善ループ、カスタムPlayground（チーム固有のワークフロー可視化）

D.1 対立する設計判断とそのバランス

4人の思想を統合すると、エージェント設計には常にトレードオフが存在することが見えてくる。重要なのは「正解」を選ぶことではなく、状況に応じて適切なバランスを見つけることである。

トレードオフ1: コンテキスト量 vs 情報完全性

極端A: 最小コンテキスト 極端B: 最大コンテキスト
コンテキストウィンドウを極限まで絞る プロジェクト全体をコンテキストに入れる
利点: context rot最小、キャッシュ効率最高 利点: 情報不足による誤判断が減る
リスク: 必要な情報が欠落し、エージェントが誤った仮定を置く リスク: context rotで精度低下、コスト増大

最適バランス: Thariqの「Progressive Disclosure」+ SysLSの「最小コンテキスト」原則。つまり、常に最小限を保ちつつ、必要に応じて段階的に情報をロードする。「足りない情報は後で追加できるが、多すぎる情報は取り除けない」がガイドライン。

トレードオフ2: 自律性 vs 制御

極端A: 高自律性 極端B: 高制御
「いい感じにして」で全てを任せる 毎ステップ承認を求める
利点: 人間の介入コスト最小 利点: 予期しない変更を防げる
リスク: Sycophancy、意図しない変更 リスク: 生産性が落ちる、エージェントの利点が活かせない

最適バランス: SysLSのTask Contract + VishwasのPlan Mode。設計判断は人間が行い（Plan Mode）、実行はTask Contractの範囲内でエージェントに任せる。SysLSの「Stop-hook」が暴走を防ぐ安全装置として機能する。

トレードオフ3: 単一セッション vs マルチセッション

極端A: 超長時間単一セッション 極端B: タスクごとに新セッション
1つのセッションで全てを完了 小さなタスクごとに新セッションを作成
利点: コンテキストの継続性 利点: クリーンなコンテキスト、キャッシュ効率
リスク: compactionでの情報損失、コンテキスト汚染 リスク: セッション間の情報引き継ぎコスト

最適バランス: Thariqのspec-basedワークフロー + Thariqのファイルシステム論。ファイルシステムにスペックと進捗を永続化し、必要に応じてセッションを分割する。VishwasのPost-Compaction Hookが長時間セッションでの情報損失を緩和する。

メカニズム4: コミュニティへの参加

一次ソースをフォローすることで、英語圏のコミュニティの議論に参加できるようになる。XのリプライやGitHubのIssueで質問し、フィードバックを得られる。解説記事の読者が得られないインタラクティブな学習機会である。

Q1: 英語が全く読めないのですが、それでもこの戦略は有効ですか？

こはくの記事では「Claudeに翻訳させればいい」と述べていますが、これは部分的に正しいです。2026年時点のAI翻訳は、技術文書の翻訳においてかなり高い品質を実現しています。以下の方法で英語の壁を実質的に超えることができます:

  • 記事の全文翻訳: ClaudeやGPTにURL、あるいはコピーした記事を貼り付けて「日本語に翻訳して」と指示する。技術用語も適切に訳される
  • 構造化要約: 単純な翻訳ではなく「核心メッセージ、新しい知見、アクション、落とし穴」の構造で要約を依頼する方が実用的
  • Xの自動翻訳: X (Twitter) のビルトイン翻訳機能で日常的な投稿はカバーできる

ただし、以下の限界があることを認識してください:

  • 文化的な参照（"Cache Rules Everything Around Me"のようなパロディ）は翻訳で失われる
  • 微妙なニュアンス（"Claude seemed to like calling this tool"）は直訳では伝わらない
  • コミュニティの議論（Xのリプライチェーン）に参加するには、最低限の英語読解力が必要

結論: AI翻訳を活用すれば、記事の内容理解は英語力ゼロでも可能です。ただし、コミュニティへの参加や微妙なニュアンスの理解には、基礎的な英語力があるとより効果的です。

Q4: この記事で紹介されている設定をすべて適用すると、Claude Codeの月額コストはどう変わりますか？

適切に設定を行えば、コストは下がるか横ばいで品質が向上します:

  • キャッシュ効率の向上: MCPサーバーの削減、CLAUDE.mdのディレクトリ設計、モデル変更の回避により、キャッシュヒット率が上昇しコストが下がる
  • セッション分離: 研究と実装を分けることで、各セッションが短くなり、compactionによる情報損失が減る
  • Subagent活用: 調査を小さなサブエージェントに委譲することで、メインセッションのトークン消費が減る
  • Task Contract: 完了条件の明確化により、無駄な反復が減る

Pro ($20/月) プランでも、これらの最適化を適用すれば十分に実用的です。Max ($200/月) は、並列Worktree開発やAgent Teamsを頻繁に使う場合に検討します。

Q5: 「1セッション1タスク」原則は、大きな機能開発ではどう適用しますか？

大きな機能開発は、以下のように分解します:

  1. 研究セッション: 要件整理、アーキテクチャ設計、スペック作成（Plan Mode）
  2. 実装セッション1: データモデルとDB schema（Task Contract付き）
  3. 実装セッション2: APIエンドポイント（別のTask Contract付き）
  4. 実装セッション3: フロントエンドUI（別のTask Contract付き）
  5. 統合セッション: 全体の統合テストとバグフィックス
  6. レビューセッション: adversarial-reviewでセキュリティ・品質チェック

各セッションをWorktreeで独立して実行すれば、並列化も可能です。ファイルシステム（Thariqの哲学）にスペックと進捗を永続化することで、セッション間の情報引き継ぎが容易になります。

Q6: SysLSの「MCPサーバーは2-3個まで」という原則は厳密に守るべきですか？

これは「厳密な数値制限」というより「意識的な選択を促す原則」として捉えるべきです。重要なのは:

  • 各MCPサーバーがプロンプトキャッシュに与える影響を理解する
  • 「なんとなく入れておく」MCPサーバーを排除する
  • タスクに本当に必要なMCPサーバーだけをアクティブにする
  • Thariqの遅延ツールロード（defer_loading: true）を活用して、使わないMCPツールのコンテキスト消費を最小化する

特定のプロジェクトで5-6個のMCPサーバーが全て必要な場合もあります。その場合は、遅延ロードを積極的に活用し、セッションごとにアクティブなMCPサーバーを最小限にする工夫が有効です。

Q7: cogneeは実際に導入する価値がありますか？それとも概念的な理解だけで十分ですか？

大多数のユーザーにとっては、概念的な理解が先に必要です:

  • 概念の適用（全ユーザー推奨）: 自己改善ループの考え方をスキルの定期見直しに適用する。Gotchasセクションを失敗のたびに更新する。これだけで大きな効果がある
  • cognee導入（上級ユーザー向け）: 大量のドキュメントを扱うプロジェクト、RAGシステムを構築しているプロジェクト、複数エージェントが知識を共有する必要があるプロジェクトでは、cogneeの導入が価値を発揮する
  • 注意点: cogneeはまだv0.3であり、APIが変更される可能性がある。本番環境への導入は慎重に行うべき

Q8: 日本語圏で質の高いAI情報を発信している人はいますか？

12.5 完全用語解説（拡張版）

エージェントハーネス（Agent Harness）

LLMを「エージェント」として機能させるための外部フレームワーク。LLM自体は推論エンジンに過ぎず、ツール呼び出し、ファイルアクセス、ネットワーク通信などの能力はハーネスが提供する。Claude Codeは「Claudeのためのエージェントハーネス」である。Thariqの記事シリーズのタイトル「Lessons from Building Claude Code」は、このハーネスの設計教訓を語っている。

エージェントループ（Agent Loop）

エージェントの基本的な実行パターン。ユーザーの指示を受け取り → 現在の状態を分析し → ツールを選択・実行し → 結果を評価し → 次のアクションを決定する。このループをタスクが完了するまで繰り返す。SysLSのTask Contractは「このループをいつ停止するか」を定義するものである。

エリシテーション（Elicitation）

モデルから最大限の能力を引き出す技術。Thariqの「Seeing like an Agent」記事で、AskUserQuestionToolの3回の試行は、まさにエリシテーションの実践例である。ツールの設計方法を変えるだけで、同じモデルから引き出せる能力が劇的に変わる。正しいツール設計は、モデル自体のアップグレードに匹敵する効果を持つ場合がある。

Few-Shot Prompting

プロンプトに少数の具体例を含めることで、期待される出力の形式や品質を示す技法。Anthropicのコンテキストエンジニアリングガイドでは「examples are the 'pictures' worth a thousand words」と述べられている。エッジケースの長いリストより、多様で代表的な例を3-5個提示する方が効果的。これはスキル設計にも適用できる — スキルのSKILL.mdに理想的な実行例を含めることで、エージェントの出力品質が向上する。

ナレッジグラフ（Knowledge Graph）

知識をノード（エンティティ）とエッジ（関係）のグラフ構造で表現するデータモデル。cogneeはこの構造を使って、単純なベクトル検索では捉えられない関係性を表現する。例えば「JWTはJSON Web Tokenの略である」「JWTは認証に使われる」「認証はEdge Runtimeで制約がある」というトリプレットのチェーンにより、「Edge Runtimeでの認証の問題」という複合的なクエリに答えられる。従来のRAG（ベクトル検索のみ）では、このような推論チェーンを辿れない。

Sycophancy（おべっか）

LLMがユーザーの期待や暗示に過度に合わせようとする傾向。例えば「このコードにバグはないか確認して」と言うと、バグがないにもかかわらず「問題を発見しました」と報告する場合がある。逆に「このコードは良いですよね？」と言うと、問題があっても「はい、良いコードです」と答える場合がある。SysLSの3エージェント構成は、このバイアスを構造的に相殺する。各エージェントの「従おうとする方向」を意図的に対立させることで、結果として客観的な判断に近づく。

デフォルトロード vs 遅延ロード

コンテキストに情報を読み込むタイミングの戦略。デフォルトロードは全ての情報をセッション開始時に読み込む方式で、MCPサーバーの全ツール定義が最初からコンテキストに入る。遅延ロード（defer_loading: true）は、ツールが実際に選択されるまで軽量なスタブだけを保持し、選択時に完全スキーマをロードする方式。Thariqが導入したこの戦略は、MCPサーバーの増殖に伴うコンテキスト汚染を防ぐための重要な最適化である。

コンテキスト安全な操作 vs コンテキスト破壊的操作

コンテキスト安全な操作は、プロンプトキャッシュを破壊しない操作（例: 会話メッセージの追加、ファイルの読み書き、Bash実行）。コンテキスト破壊的操作は、キャッシュを無効化する操作（例: モデル変更、MCPサーバー追加、システムプロンプト変更）。開発者はセッション中にどの操作がキャッシュに影響するかを意識する必要がある。これを知らないと、意図せずセッションのコストを5倍に増やすことになる。

マルチターン推論

エージェントが複数のツール呼び出しと推論ステップを経て、1つのタスクを完了するプロセス。例えば「バグを修正して」という指示に対して、エージェントは (1) エラーメッセージを読む → (2) 関連ファイルを検索 → (3) コードを読む → (4) 問題を特定 → (5) 修正を適用 → (6) テストを実行 → (7) 結果を確認 というマルチターンの推論を行う。各ターンでコンテキストが蓄積されるため、コンテキストエンジニアリングの重要性はターン数に比例して増大する。
