図4：[A] テキストコーパス② — 正本(text/)と索引(shards/)の分離

全ドメインに反復する正準構造。text/=真実の源、shards/=発見用TSV索引、_shard_routing.json=横断ルータ

操作読み込み回数トークン適用
直接アクセス1回0.3-10K条文/通達/別表/QA（ID判明時）
shard検索 → 本文3回8-15K判決/QA/文献/条約（ID不明時）
10論点横断（直接）10回30-50K最適
10論点横断（shard）30回100-150Kコンテキスト圧迫（避ける）

【設計の核心】役割分離

text/ は完全な本文（遅いが正確）、shards/ は事前分割された TSV メタデータ（速い発見用）、index.json は shard 一覧（範囲検索を可能に）、_shard_routing.json は全ドメイン横断ルータ（topic/doc_code → 対象 shard）。この4段により「ID判明→1読」を担保しつつ、未知の論点には段階的 narrowing を提供する。

図5：[A] テキストコーパス③ — 命名規則とヘッダー形式

区切り文字3種が意味を持つ。これがユーザー質問→パスの「一発変換」を可能にする（llms.txt の鉄則）

ヘッダー形式（3系統）

図7：ビルド・保守パイプライン（Python 20本）

RAW（e-Gov法令API・NTAサイト）→ text/ → 保守・検証 → shards/ → ルーティング → GitHub Pages 配信

【トークン閾値とゲート】

MAX_TOKENS=9999（tiktoken cl100k_base）が全体の駆動制約。split_oversized は target 9,900tok で分割、lean_shards は shard を ≤9,500tok に再パック。閾値の駆動理由は GitHub Pages やファイルサイズではなく LLMのコンテキストウィンドウ。各 build スクリプトは末尾で split_oversized＋verify_integrity を自走する。

⚠️ ビルダが存在しないドメイン

qa / hanketsu / guide / accounting / paper / treaty の text/ には生成スクリプトが無い。migrate.py 内の旧URL（…/html-preview/ai-nta-qa-db/…）から、前身リポジトリ群（ai-nta-qa-db 等）からの移植と判明。条文系（law/別表/実特法/耐用年数）のみ本リポジトリ内ビルダを持つ。
