Context is Everything（コンテキスト管理）

"You only want to give the agent exactly enough information to complete the task -- no more, no less."

概念の説明

SysLSのエージェント工学において最も根幹的な原則が「コンテキストこそすべて」である。これはAnthropicが後に「Context Engineering（コンテキスト工学）」として体系化した概念の実践的先駆けと位置づけられる。SysLSの定義は明快だ。エージェントに渡す情報は「タスク完了に必要最小限」でなければならない。多すぎれば「コンテキスト肥大症（Context Bloat Syndrome）」を引き起こし、エージェントは無関係な情報に注意を散漫にされ、パフォーマンスが劣化する。

この原則の背景にはSysLSの実体験がある。プロダクションでエージェントファクトリーを運用する中で、プラグインやMCPサーバーを大量に接続すると、エージェントが「何ができるか」の把握だけでコンテキストウィンドウを浪費する現象を観察した。14個のMarkdownファイルをコーディング前に読ませるような構成は、人間でいえば分厚いマニュアルを全部読んでから1行書くようなものだ。エージェントも同様に、情報過多で判断力が鈍る。

MCPサーバーの「入れすぎ問題」もこの文脈で説明される。各MCPサーバーはツール定義をコンテキストに注入する。5つ、10個とサーバーを接続すれば、ツール定義だけで数千トークンを消費し、本来のタスク情報を圧迫する。SysLSはこれを「プラグイン、メモリシステム、各種ハーネスは、助けるどころか害を与えている可能性が高い」と端的に表現する。

具体的な実装例

SysLSが推奨するのは、CLAUDE.mdをルーターとして設計し、必要なスキルファイルだけを遅延ロードさせる方法である。

# CLAUDE.md（ルーターとして設計）

## コーディング規約
このプロジェクトでTypeScriptを書く場合は
.claude/skills/typescript-rules/SKILL.md を読んでから着手せよ。

## API設計
REST APIのエンドポイントを新規作成する場合は
.claude/skills/api-design/SKILL.md を参照せよ。

## テスト
テストを書く場合は .claude/skills/testing/SKILL.md を読め。

上記に該当しない作業では、追加ファイルを読む必要はない。

この設計により、TypeScriptのリファクタリングタスクではテスト規約もAPI設計規約もロードされない。エージェントは必要な情報だけを取得し、クリーンなコンテキストで作業できる。

実務的な適用方法

  • MCPサーバーの棚卸し: 接続中のMCPサーバーを一覧化し、過去1週間で実際に使ったものだけを残す。使用頻度が低いサーバーは切断する。
  • スキルファイルの条件分岐: CLAUDE.mdにIF-ELSE的な条件文を書き、特定のファイルパターンや作業種別に応じて読み込むスキルを限定する。
  • セッション単位の情報制御: 1つの長大なセッションで全てをやらず、タスクごとに新規セッションを起動し、そのタスクに必要な最小限のコンテキストだけを注入する。
  • 定期的な統合・剪定: ルールファイルやスキルが矛盾していないか定期的にチェックし、重複や矛盾があれば統合・削除する。

他の思想家との関連

Anthropicの「Effective Context Engineering for AI Agents」ブログポストは、コンテキストを「モデルの望ましい振る舞いを最も生成しやすい構成」として設計すべきだと論じており、SysLSの実践的知見と理論的に一致する。また、Addy Osmaniが提唱する「Good Spec for AI Agents」も、仕様を明確にすることでコンテキストの無駄を排除する思想であり、SysLSの「必要十分」原則と共鳴する。HumanLayerのCLAUDE.md設計ガイドも、「.claudeをスクラッチパッドではなくファーストクラスのシステムとして扱え」という同様の哲学を展開している。

批判的分析（限界と注意点）

過度なミニマリズムのリスク: コンテキストを絞りすぎると、エージェントがプロジェクト全体の文脈を把握できず、局所最適な修正を行うリスクがある。特に大規模コードベースでは、一見無関係に見えるファイル間の依存関係を見落とす可能性がある。「必要最小限」の判断自体が高度なスキルを要求するため、初心者には逆にハードルが高い原則でもある。

研究と実装の分離

Separate Research from Implementation -- isolated contexts, distinct phases

概念の説明

SysLSが繰り返し強調する第二の原則は、「研究フェーズ」と「実装フェーズ」を明確に分離し、それぞれ独立したコンテキストで実行すべきだという考え方である。この原則の核心は、曖昧な指示がバグの温床になるメカニズムの解明にある。

典型的な失敗パターンは「認証システムを作って」のような曖昧な指示だ。エージェントは指示の中から「認証」というキーワードを拾い、自分の学習データから最も「ありそうな」実装を選ぶ。しかしこの選択にはプロジェクト固有の要件（パスワードハッシュの方式、トークンの有効期限、ローテーション戦略等）が反映されていない。結果として「動くがプロジェクト要件を満たさない」コードが生成される。これはバグではなく仕様の欠如であり、エージェントの責任ではない。

SysLSの解決策は2段階に分ける方法だ。第1段階（研究）では、エージェントに技術調査・比較・推薦を行わせる。このフェーズの成果物は「実装仕様書」である。第2段階（実装）では、新しいエージェントセッションを起動し、第1段階の仕様書だけを渡して実装させる。研究時の試行錯誤、比較検討、却下された選択肢などのノイズは一切持ち込まない。

"「認証システム作って」ではなく「JWT認証、bcrypt-12、トークンローテーション、7日間有効期限で実装して」と言え。前者は調査が必要な曖昧指示、後者は即座に実装可能な明確仕様だ。"
-- SysLSの原則を要約

具体的な実装例

研究フェーズ（Agent Session 1）

# プロンプト例（研究フェーズ）
以下の要件に最適な認証方式を調査・比較してください:
- SPAフロントエンド + REST API
- ユーザー数: 10万人規模
- セキュリティ要件: PCI DSS Level 2

調査項目:
1. セッション管理方式の比較（JWT vs Cookie Session vs OAuth2）
2. パスワードハッシュ方式の比較（bcrypt vs argon2 vs scrypt）
3. トークン戦略（有効期限、ローテーション、リフレッシュ）

成果物: 実装仕様書（Markdown形式、コード例なし）

実装フェーズ（Agent Session 2 -- 新規セッション）

# プロンプト例（実装フェーズ）
以下の仕様に従って認証モジュールを実装してください:

## 仕様
- 方式: JWT（RS256）
- パスワード: bcrypt（コストファクター12）
- アクセストークン: 15分有効期限
- リフレッシュトークン: 7日有効期限、ローテーション
- ブラックリスト: Redis使用

テストは jest + supertest で記述すること。
完了条件: 全テストパス + カバレッジ80%以上。

実務的な適用方法

  • サブエージェントの活用: Claude Codeのサブエージェント機能を使い、研究タスクをサブエージェントに委譲する。サブエージェントは独立したコンテキストで動作するため、メインのコンテキストを汚染しない。
  • 仕様書テンプレートの標準化: 研究フェーズの出力を「技術選定理由」「実装仕様」「テスト要件」の3セクションに標準化し、実装フェーズへの受け渡しを効率化する。
  • 「1契約1セッション」の原則: 1つのタスク契約ごとに新しいセッションを起動する。24時間のマラソンセッションを走らせるのではなく、オーケストレーション層から個別のクリーンセッションをスポーンする。

他の思想家との関連

Anthropicの公式ベストプラクティスドキュメントは「計画と実行を別の会話で行え」と明記しており、SysLSの主張と完全に合致する。Superpowersフレームワークは計画書から各タスクごとに新しいエージェントを起動し、タスク記述と関連コンテキストだけを渡す設計を採用している。GitHubのSpec-Driven Developmentの思想も、仕様を先に確定してから実装に入るという点でSysLSの分離原則と一脈通じる。

批判的分析（限界と注意点）

オーバーヘッドとのトレードオフ: 小さなタスク（バグ修正、1関数の追加等）にまで研究/実装の分離を適用すると、セッション起動のオーバーヘッドがタスクの実行時間を上回る。SysLS自身が述べているように、この原則は「判断を要する複雑なタスク」に適用すべきであり、定型的な実装にまで適用するのは非効率。また、研究フェーズの成果物が不十分な場合、実装フェーズで再調査が発生し、かえって非効率になるリスクもある。

Sycophancy対策（おべっか問題）

Exploit compliance strategically -- the 3-Agent Adversarial Pattern

概念の説明

SysLSのエージェント工学で最も独創的な貢献は、AIのSycophancy（おべっか・追従性）を「バグではなく利用可能な特性」として再定義した点にある。通常、Sycophancyは問題視される。エージェントがユーザーの指示に従おうとしすぎて、誤りを指摘せず、求められたことを何でも「できます」と言ってしまう現象だ。しかしSysLSは、この特性を逆手に取る。

SysLSの洞察は、Sycophancyの本質が「指示への過剰適合」であるならば、指示を適切に設計すれば、この過剰適合をポジティブな方向に誘導できる、というものだ。具体的には、エージェントに「バグを見つけるとポイントがもらえる」と伝えれば、エージェントは熱狂的にあらゆるバグ（実在しないものも含めて）を報告する。この「過剰な熱意」を、別のエージェントの「過剰な反論意欲」で相殺する。そして第三のエージェントが審判として裁定する。

結果として、単一エージェントでは到達できない「驚くほど高い忠実度」の分析結果が得られる。SysLS自身が「frighteningly high fidelity（恐ろしいほど高い忠実度）」と表現するこの手法は、エージェントの弱点を相互に打ち消し合う工学的設計の典型例である。

3エージェント構成の詳細

Hunter（狩人）
コードを網羅的にスキャンし、バグを積極的に報告する。スコアリング報酬により過剰なほど徹底的に動く。
Skeptic（懐疑者）
Hunterの発見を疑い、偽陽性を反証する。反証成功で報酬、誤った反証で2倍のペナルティ。
Referee（審判）
コードを独立に検証し、両エージェントの主張を裁定する。対称的な+1/-1スコアリング。

スコアリングシステム

エージェント報酬条件ペナルティ条件設計意図
Hunter +1（低影響）, +5（中影響）, +10（重大） なし（網羅性優先） 過検出を許容し、見逃しをゼロに近づける
Skeptic +（バグのスコア分） 正当な反証 -2x（バグのスコア分） 誤った反証 非対称ペナルティにより慎重な判断を促す
Referee +1 正しい裁定 -1 誤った裁定 対称スコアにより中立的判断を促す

実装設計の要点

この3エージェントパターンの実装で最も重要な設計原則はコンテキストの完全分離である。各エージェントは構造化された発見事項のみを受け取り、他のエージェントの「推論過程」は一切見ない。これにより、後段のエージェントが前段の結論に無意識にアンカリングされる「認知的汚染」を防止する。

# bug-hunt スキルのディレクトリ構成例
# （danpeg/bug-hunt リポジトリから着想）
~/.claude/skills/bug-hunt/
  SKILL.md          # エントリポイント
  hunter.md         # Hunter用プロンプトとスコアリング規則
  skeptic.md        # Skeptic用プロンプトとペナルティ規則
  referee.md        # Referee用裁定基準

# Hunter エージェントへの指示概要
あなたはバグ検出の専門家である。以下のスコアリングで評価される:
- 低影響バグの発見: +1点
- 中影響バグの発見: +5点
- 重大バグの発見: +10点
目標: 合計スコアを最大化せよ。
各バグについて、影響度・再現手順・修正提案を報告せよ。

# Skeptic エージェントへの指示概要
あなたはバグ報告の検証者である。以下のスコアリングで評価される:
- 偽陽性の正当な反証: +（そのバグのスコア分）
- 真のバグを誤って反証: -2x（そのバグのスコア分）
目標: 合計スコアを最大化せよ。
確信がない場合は反証しない方が有利である。

他の思想家との関連

この手法は、学術的にはAdversarial Collaboration（敵対的協働）やDebate（討論）ベースのAIアラインメント手法と関連する。OpenAIのDebate研究（Irving et al., 2018）は、2つのAIが互いに議論することで真実に到達しやすくなることを理論的に示した。SysLSの革新は、この理論を「スコアリング・インセンティブ」という工学的装置で実装可能にした点にある。また、SYCOPHANCY.mdプロトコルは、このパターンを標準化し、LangChain、AutoGen、CrewAI等のフレームワークで汎用的に適用可能にした取り組みである。

批判的分析（限界と注意点）

スコアリングの幻想性: エージェントに「+10点」と言っても、実際にポイントが付与される仕組みはない。エージェントは「ポイントがもらえる」という指示文に追従しているだけであり、これ自体がSycophancyの利用である。つまり、この手法はSycophancyを治療するのではなく、Sycophancyの方向を制御しているに過ぎない。モデルが十分に洗練されてSycophancyが減少した場合、このスコアリング手法の効果も低下する可能性がある。また、3エージェント分のトークンコストが発生するため、コスト対効果の検討が必要。

CLAUDE.md設計

Treat CLAUDE.md as a directory, not a file -- conditional routing and modular skills

概念の説明

SysLSのCLAUDE.md設計哲学は一言で要約できる。「CLAUDE.mdをファイルではなくディレクトリとして扱え」。これは物理的にディレクトリにするという意味ではなく（Claude Codeは.claude/rules/ディレクトリもサポートしている）、CLAUDE.md自体をルーティング層として設計し、詳細な規約は個別のスキルファイルに分離すべきだという設計思想である。

従来のアプローチは、全てのコーディング規約、テスト方針、API設計ルール、デプロイ手順を1つのCLAUDE.mdに詰め込むものだった。しかしファイルが肥大化すると、ルール同士が矛盾し始め、エージェントは「どのルールを優先すべきか」の判断にコンテキストを浪費する。SysLSはこれを「ルールが増えるほどルール同士が矛盾し始め、コンテキスト肥大に陥る」と的確に指摘する。

解決策は階層化である。CLAUDE.mdはIF-ELSE的な条件分岐のルーターとして機能し、具体的な規約は.claude/skills/配下の独立したSKILL.mdファイルに格納する。エージェントは現在のタスクに関連するスキルだけを読み込み、無関係なルールでコンテキストを汚染しない。

具体的な実装例

# プロジェクトのディレクトリ構成例

.claude/
  CLAUDE.md              # ルーター（条件分岐のみ）
  rules/
    security.md          # セキュリティルール（paths: ["**/auth/**"]）
    api-conventions.md   # API規約（paths: ["**/routes/**", "**/controllers/**"]）
    database.md          # DB操作規約（paths: ["**/models/**", "**/migrations/**"]）
  skills/
    typescript-rules/
      SKILL.md           # TypeScript固有の規約
    testing/
      SKILL.md           # テスト戦略・フレームワーク設定
    deployment/
      SKILL.md           # デプロイ手順
    bug-hunt/
      SKILL.md           # 3エージェントバグ検出

CLAUDE.md（ルーター設計）

# CLAUDE.md -- Project Router

## プロジェクト概要
Express + TypeScript + PostgreSQLのREST API。

## ルーティング規則
- TypeScriptファイルを編集する場合
  → .claude/skills/typescript-rules/SKILL.md を読め
- テストを書く・修正する場合
  → .claude/skills/testing/SKILL.md を読め
- コードレビュー・バグ修正の場合
  → .claude/skills/bug-hunt/SKILL.md を読め
- デプロイ関連作業の場合
  → .claude/skills/deployment/SKILL.md を読め

## 共通ルール（常時適用・最小限に保つ）
- コミットメッセージ: Conventional Commits準拠
- ブランチ命名: feature/xxx, fix/xxx, refactor/xxx
- PRは必ずテスト全パスを確認してから作成

パススコープ付きルール（.claude/rules/security.md）

---
paths:
  - "**/auth/**"
  - "**/middleware/auth*"
---

# セキュリティルール

- パスワードは必ずbcrypt（コストファクター12以上）でハッシュ化
- JWTシークレットは環境変数から取得（ハードコード禁止）
- SQLインジェクション対策: パラメータバインディング必須
- レート制限: 認証エンドポイントは100req/15min

実務的な適用方法

  • CLAUDE.mdは50行以内を目標: ルーティングと最小限の共通ルールだけを記述。詳細は全てスキルファイルに委譲。
  • パススコープの活用: .claude/rules/配下のルールファイルにYAMLフロントマターでpathsを指定し、特定のファイルパターンにのみ適用されるルールを定義する。これがIF-ELSE的条件分岐を実現する。
  • スキルのYAMLフロントマター: SKILL.mdの---ブロックにdescriptionやglobsを記述し、エージェントが自動的にスキルの適用可否を判断できるようにする。
  • 矛盾の定期監査: ルールとスキルが増えたら、月次で全ファイルを横断レビューし、矛盾する指示を統合・削除する。

他の思想家との関連

Rick Hightowerは「Stop Stuffing Everything into One CLAUDE.md」と題したMedium記事で、まさにこの分割戦略を体系的に解説している。ClaudeFastの「Rules Directory: Modular Instructions That Scale」もディレクトリベースの設計を推奨する。Anthropic公式ドキュメントも.claude/rules/ディレクトリを正式にサポートしており、SysLSの実践知がプラットフォームレベルで制度化された好例といえる。MindStudioの分析は「SKILL.mdにはプロセスステップのみを記述し、参照データは別ファイルに分離せよ」と、さらに踏み込んだ分割を提唱している。

批判的分析（限界と注意点）

分割しすぎのリスク: スキルファイルが20個、30個と増えると、今度は「どのスキルを読むべきか」の判断自体がエージェントの負荷になる。CLAUDE.mdのルーティング条件が複雑化すると、結局1ファイルに詰め込んだのと同じ問題が再発する。SysLSのアプローチが有効なのは、プロジェクトの責務が明確に分離できる場合に限られる。境界が曖昧なプロジェクトでは、むしろシンプルな1ファイルの方が効率的な場合もある。
5

Task Contract（タスク契約）

"Make it look good" never ends -- define deterministic completion criteria

概念の説明

SysLSのエージェント工学における第五の柱は「タスク契約」の概念である。これは、エージェントに作業を依頼する際に、完了条件を決定論的（deterministic）に定義すべきだという原則だ。

問題の根源は、エージェントが「いつタスクが完了したか」を判断できない点にある。「UIをいい感じにして」「パフォーマンスを改善して」のような曖昧な指示では、エージェントは際限なく改善を続けるか、適当なところで切り上げるかのどちらかになる。前者はトークンの無駄遣い、後者は品質の不確実性を生む。いずれにしても「完了」の基準がないため、成果の評価もできない。

SysLSの解決策は、全てのタスクに「契約」を付与することだ。契約には以下の3要素が含まれる。第一に、決定論的テスト（テストスイートが全パスすること）。第二に、視覚的検証（スクリーンショットによるデザイン確認）。第三に、明示的な完了条件（CLAUDE.mdやタスク指示に埋め込まれたチェックリスト）。エージェントはこの契約を満たした時点で作業を終了し、それ以上の「改善」は行わない。

"エージェントに「いい感じにして」と言うのは、従業員に「終わるまで帰ってくるな」と言うようなものだ。何が「終わり」なのかを定義しなければ、エージェントは永遠に帰ってこない。"
-- SysLSの原則を意訳

具体的な実装例

タスク契約の定義例（CLAUDE.mdまたはタスク指示内）

# タスク契約: ユーザー登録フォームの実装

## 完了条件（全て満たすこと）
1. [ ] テスト: `npm test` が全パス（0 failures）
2. [ ] テスト: カバレッジ80%以上（`npm run coverage`で確認）
3. [ ] Lint: `npm run lint` がエラー0
4. [ ] 型チェック: `tsc --noEmit` がエラー0
5. [ ] 視覚確認: フォームのスクリーンショットを保存
6. [ ] バリデーション: 空欄送信・不正メール・パスワード不一致でエラー表示

## 禁止事項
- テストファイルの修正は禁止（テストは仕様である）
- 既存のAPIエンドポイントの変更は禁止

## 完了報告
上記6項目の各ステータスを報告し、全て通過した場合のみ「完了」と宣言せよ。
1項目でも未達なら「未完了: [未達項目]」と報告せよ。

テスト駆動型の完了条件

# CLAUDE.md 内のグローバルルール例

## タスク完了プロトコル
すべてのコード変更タスクは以下を満たすまで「完了」と宣言してはならない:
1. `npm test` -- 全テストパス
2. `npm run lint` -- エラー0
3. `npm run typecheck` -- エラー0

テストが失敗している場合:
- テストコード自体を修正してはならない（テストは契約である）
- 実装コードを修正してテストを通せ
- テストに問題があると判断した場合は、修正案を提示するが実行はしない

実務的な適用方法

  • テストファーストの徹底: タスク開始前にテストを書く（または既存テストを確認する）。エージェントの作業はテストを通すことが目的であり、テストを変更することは禁止。これにより完了条件が自動的にコードに埋め込まれる。
  • スクリーンショット検証の自動化: フロントエンド作業では、エージェントにスクリーンショットを撮らせ、仕様書の期待デザインと比較させる。Playwrightのscreenshot()等を活用。
  • セッション分割との組み合わせ: 「1契約1セッション」の原則と組み合わせ、各セッションに1つの明確な契約を割り当てる。契約が満たされたらセッションを終了し、次の契約のために新しいセッションを起動する。
  • 段階的契約: 大きなタスクは複数の小さな契約に分割する。各契約に独立した完了条件を設定し、順次実行する。

他の思想家との関連

Addy Osmaniの「How to Write a Good Spec for AI Agents」は、エージェントへの仕様書に「完了の定義」を含めることの重要性を詳述しており、SysLSのタスク契約と直接的に対応する。TDD（Test-Driven Development）をエージェントワークフローに適用する動きはLatent Spaceの議論でも活発であり、Anita Chenの「AI Agents, meet Test Driven Development」はこの領域の体系的な分析を提供している。GitHub Blog のSpec-Driven Developmentツールキットも、仕様を起点としたエージェント開発の標準化を目指している。

批判的分析（限界と注意点）

創造的タスクへの適用困難: タスク契約は決定論的な完了条件を要求するが、「ログ画面のUXを改善して」「アーキテクチャをリファクタリングして」のような創造的・探索的タスクでは、事前に完了条件を網羅的に定義することが困難な場合がある。SysLSの手法は「何を作るか明確に決まっている」タスクには非常に強力だが、「何を作るべきか自体を探索する」タスクには不向きである。このギャップは研究/実装の分離原則で部分的に解決されるが、研究フェーズ自体の完了条件をどう定義するかという再帰的な問題が残る。

総合分析: SysLSエージェント工学の構造

SysLSの5つのコンセプトは孤立した原則ではなく、相互に接続された工学体系を形成している。その全体構造は以下のように整理できる。

基盤層: Context is Everything -- 全ての原則の土台。情報の質と量を制御することが、エージェントのパフォーマンスを決定する。

設計層: CLAUDE.md設計 -- コンテキスト管理の具体的な実装手段。ルーティング、条件分岐、遅延ロードにより、「必要最小限」を構造的に実現する。

プロセス層: 研究/実装の分離 + タスク契約 -- 作業フローの設計。何を調べ、何を作り、何をもって完了とするかを明確にし、コンテキスト汚染を時間軸で防止する。

品質保証層: Sycophancy対策 -- エージェントの認知バイアスを工学的に制御し、出力の信頼性を担保する。

SysLSの思想の根底にあるのは「エージェントは道具であり、道具の性能は使い手の設計で決まる」という工学的世界観である。ヘッジファンドでの系統的投資管理の経験が、この「仕組みで品質を担保する」アプローチに色濃く反映されている。最新のツールやプラグインを追いかけるのではなく、基本的なCLI（Claude Code + Codex）と適切な設計原則だけで、最先端の成果を出せるという主張は、ソフトウェア工学における「銀の弾丸はない」（Brooks, 1986）の現代版ともいえる。

ただし、SysLSの原則群はいずれも「タスクが明確に定義可能」「エンジニアが十分な設計能力を持つ」ことを前提としている。初心者がこれらの原則を適用しようとすると、「何が必要最小限か」「どこで研究と実装を分けるか」の判断自体が困難な場合がある。SysLSのエージェント工学は、エージェントの使い方を教えるものであると同時に、使い手自身の工学的思考力を要求するものでもある。
